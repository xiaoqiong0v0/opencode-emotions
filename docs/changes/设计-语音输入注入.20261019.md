# 变更说明：自动朗读 F10 独占 + ASR 接口抽象与按段传输（2026-10-19）

对应原文档：`docs/设计-语音输入注入.md` §13（命令表）、§14 背景、§14.2、§15.2、§15.3；
`docs/ASYNC.md` 交互点 ⑫⑬⑮ 与不变量、变更记录；README「热键」「`emotions_cli` 工具契约」「自动朗读」「语音配置」。

## 原（自动朗读部分）
- **开关由模型经 CLI 切换**：`emotions_cli` 工具与 `emotions-cli` 提供 `auto_tts on|off`（无参/`status` 查看状态），
  `status` 回显 `auto_tts: on|off`，`CliPhrases.autoTtsOn/Off/Failed` 与工具/帮助文案都教模型用它。
- **写入方是 CLI 子进程**：`emotions-cli` 调 `writeAutoTts()` 原子写 `auto-tts` 文件，server 插件读它决定是否朗读。
- **关掉后可能继续播**：`auto-read.ts` 只在 `handlePart`（每次事件）与 `runFallback` 开头各查一次开关；
  一旦某块进入串行队列，`drain()` 会一路把已入队的后续块播完，不复查开关。

## 现在（自动朗读部分）
- **`F10` 热键是唯一开关，模型不可切**：`src/tui.tsx` 新增 `toggleAutoRead()`（点按切 `on`/`off`，命令名
  `voice.autotts.toggle`，键 `f10`，标题/说明走 i18n `command.autoTtsTitle/Desc`）；开启只影响后续回复、**不补读历史**。
- **整体移除 `auto_tts` 命令面**：`src/voice/cli.ts`（`AutoTtsMode`/`AUTO_TTS_COMMAND`/`parseAutoTts`/`kind:"autoTts"` 分支）、
  `src/cli/emotions-cli.ts`（`runAutoTts`、`main` 的 `autoTts` 分支、`status` 两行回显、相关 import）、
  `src/lib/i18n.ts`（`CliPhrases.autoTts*`、工具描述/`args`、中英帮助行）全部删除，无旁路。
- **关闭即停**：F10 关 → `writeAutoTts(false)` + 复用 `stopPlayback()` 按 PID 停当前段；
  `auto-read.ts` `drain()` 改为**每次派生前再读一次开关**，关闭即清空队列、不再播下一段。
- **写入方改为 TUI 进程**：`auto-tts.ts` 文档、ASYNC 交互点 ⑫ 与不变量同步更新；F10 进槽位**末端状态段** `🔊 F10`（见下文「追加（同日）」，本段初版曾定「不进槽位」，同日按用户要求改为追加显示）。

## 为什么（自动朗读部分）
- 用户要求「朗读开关归用户」：自动朗读是对用户播放的行为，开关权应由用户掌握，不应由模型自行开启/关闭，
  故把唯一入口收敛到 TUI 的 `F10` 热键，并彻底移除模型可达的 CLI/工具旁路（含「关掉即停」，避免关后仍继续播）。

## 原（ASR 部分）
- **runtime 直连 `AliyunAsrClient`**：`voice-runtime.ts` 直接 `new AliyunAsrClient`；无 `AsrClient` 接口。
- **只有 WebSocket 实时传输**：`AsrProtocol` 仅 `realtime`（qwen base64 JSON）/`inference`（paraformer 裸二进制）
  两种 WS 方言；连 `--wav` 自测也按 100ms 帧模拟实时喂流，**没有「整段音频→HTTP→文本」路径**，无法接
  MiMo（`mimo-v2.5-asr`，OpenAI 兼容 HTTP）或阿里录音文件识别。
- **凭证**：ASR 一律走 `resolveCredentials`（强制 workspace），MiMo 只有 TTS 侧的 `resolveMimoApiKey`。

## 现在（ASR 部分）
- **接口抽取**：新增 `AsrClient`（`connect/feed/finish/close` + `errorMessage/isFinished`，结果/错误经构造参数
  `onResult`/`onError` 回调）与 `AsrResult` 收敛到 `src/voice/asr/types.ts`（`aliyun.ts` 再导出，旧导入路径不变）；
  `AliyunAsrClient` 实现该接口（加 `transport="stream"`），行为不变。
- **传输分类**：预设新增 `transport: "stream" | "segment"`——stream=现有两 WS 方言；segment=整段音频→HTTP→文本。
- **工厂**：`src/voice/asr/index.ts` `createAsrClient()` 按 provider 分流；`voice-runtime.ts` 改为工厂创建，
  `--wav` 自测按 `client.transport` 分流（stream 保持按帧模拟；segment 整个 WAV 作为一段发送）。
- **阿里按段 `aliyun-qwen-file`**：qwen3-asr-flash **同步** OpenAI 兼容接口（官方文档 webfetch 核：
  `POST {workspace}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/chat/completions`，base64 data URL
  ≤10MB、录音 ≤5min，`choices[0].message.content` + `annotations[0].emotion` 7 类）——有同步短音频接口，
  **不走**异步 task 提交+轮询（异步 filetrans 仅收公网 URL，麦克风 PCM 不可用）；预期延迟≈一次 RTT+推理
  （短句秒级）。
- **MiMo 按段 `mimo`**：`mimo-v2.5-asr`，同一 `chat/completions` 端点（与 TTS 同域名），非流式；
  文本取 `choices[0].message.content`，无情绪；语言口径：`language` 为 zh/en 直用，否则 hints 含 zh→zh、
  含 en→en、否则 auto。
- **分段基类** `src/voice/asr/segment.ts`：本地**最小能量静音切段**（复用 `vad.silenceDurationMs`；
  `vad.threshold` 沿用 [-1,1] 语义、能量口径 ×0.1 归一），时长上限 60s、10MB base64 红线超限均分切开
  顺序发送不丢段；纯静音段不发送；串行 drain + AbortController（`close()` abort 在途）；单段失败记脱敏
  错误后继续下一段。
- **凭证**：`mimo` ASR 走 `resolveMimoApiKey`（env `MIMO_API_KEY` > `tts.mimoCredentials`，与 TTS **物理同一份**、
  不在配置另抄）；`aliyun-qwen-file` 与 stream 相同走 `resolveCredentials`。默认 provider 不变、未知 id 回退不变。
- **复用/收敛**：WAV 打包复用 `src/voice/wav.ts`（`buildWavHeader` 自 `tts/audio-sink.ts` 收敛到 `wav.ts`，
  audio-sink 再导出）；MiMo 端点复用 `tts/mimo.ts` 的 `MIMO_API_URL`。
- **文案/文档**：`--provider` 帮助、配置模板注释、README provider 清单与凭证说明、`docs/ASYNC.md` 交互点 ⑮
  与四条不变量同步。

## 为什么（ASR 部分）
- 用户要求 ASR 同时支持**实时（stream）与按段（segment）**：实时沿用阿里 WS 两方言不变；按段新增
  阿里同步文件识别与 MiMo OpenAI 兼容 HTTP 两条链路。抽象成 `AsrClient` 接口 + 工厂后，runtime 与结果出口
  （`onFinal` → NDJSON `final` → TUI 注入）完全不变，新 provider 只是多一种传输实现。

## 追加（同日）：槽位末端追加 `🔊 F10` 自动朗读状态段

对应原文档：`docs/设计-语音输入注入.md` §3（TUI 槽位形态/宽度契约/配色表）、§14.2。

### 原
- 槽位形态 `[🎙状态][注入|输入][F8/F9]`（第三段恒 `F8/F9`），`formatSlotSegments` 固定 **6 段**、TUI 固定 **6 个 `<text>`**；
  总宽恒定 zh=16 / en=18；F10（自动朗读）**不进槽位**，只有 toast 反馈。

### 现在
- 末端追加第 7 段 ` 🔊 F10`（喇叭图标 🔊 + 键名，**固定文本、不加模式语义**）：`🎙 ●  注入 F8/F9 🔊 F10`；
  **颜色表达自动朗读开关**——激活 `autoReadActive`→`theme.success`（亮）、未激活 `autoReadInactive`→`theme.textMuted`（灰）；
  `SlotRenderState` 增 `autoReadOn`，`SlotColorRole` 增两角色；热键常量 `AUTO_READ_KEY`/`AUTO_READ_KEY_LABEL` 收敛到 `slot.ts`
  （与 `keymap` 绑定同源，`src/tui.tsx` 改用导入、删除本地重复定义）。
- **宽度恒定不破**：追加段是固定串（1 空格 + 🔊2 列 + 1 空格 + F10 三列 = **7 列**），不依赖任何状态；
  可变段定宽填充口径不变 ⇒ 任意 mic 状态 × 模式 × 语言 × 朗读开关总宽恒定（zh 16→23、en 18→25），单测新增固定列宽与两态等宽断言。
- 状态源：TUI 新增 `autoReadOn` 信号——**启动读一次** `auto-tts` 文件作初值，`F10` toggle **写成功后同步**（写失败保持原值）；
  无其它写入方（模型侧 `auto_tts` 已移除），不监听文件。

### 为什么
- 用户指定形态：状态条要能一眼看出自动朗读开/关，且**只是状态**（不是模式、不加文字）；
  喇叭段图标与键名都是常量，追加后仍满足既有「总宽恒定」契约，无需动定宽算法。
