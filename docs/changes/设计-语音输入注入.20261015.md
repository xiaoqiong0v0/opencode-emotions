# 变更说明：流式 TTS + 打断（barge-in）+ 增量自动朗读（2026-10-15）

对应原文档：`docs/设计-语音输入注入.md` §11.3、§14、新增 §15；`docs/ASYNC.md` 交互点 ⑩⑫⑬与不变量；README「语音输出 / 音频落地 / 自动朗读 / 已知限制」。

## 原
- **`aliyun` 是整段合成**：`run-task` → 收 `task-started` → 一次 `continue-task`（全量正文）→ `finish-task`，
  在**收齐全部二进制帧**（等 `task-finished`）后才 `Buffer.concat`，非 wav 用 ffmpeg 转码、落临时 WAV
  （流式 WAV 头占位长度经 `normalizeWavHeader()` 重写），最后交给**文件播放器**（`player.ts`）播放。**首包延迟高**。
- **无法打断**：播放由不同进程发起（工具/自动朗读各自的 CLI `speak` / 分离 `__play`），跨进程无句柄；
  `dispose` 不再 `stop`，用户发消息或语音输入时正在播放的语音不会停。
- **自动朗读是「消息完成→整段读」**：`event` 钩子只在 `message.updated` 完成时触发，取回全部 parts 整段朗读。

## 现在
- **流式合成 + 边收边播**（`src/voice/tts/aliyun.ts` 重写）：
  - 增量送文：`chunkText()` 按句切多条 `continue-task`（单条 ≤ `CONTINUE_CHUNK_CHARS`(200)、累计 ≤ `MAX_TOTAL_CHARS`(20 万)）；
  - `format` **强制 `pcm`**，二进制帧**到达即写 AudioSink**；`task-finished` 后等 `AudioSink.end()` 真正播完；
  - 新增 `buildCosyVoiceCancelTask()`（`finish-task` + `payload.input.directive="cancel"`）与 `stop()` 取消；
  - `instruction` 据实校验：新增 `supportsInstruction(model)`，仅 v3/v3.5 与 qwen-audio-3.x；v2 忽略并记日志。
- **AudioSink**（新增 `src/voice/tts/audio-sink.ts` + `stream-player.ts`）：首选**流式**（吃 stdin raw PCM 的
  `aplay`/`paplay`/`sox play`/`ffplay`）→ 回退**分段**（PCM 按 ~1.5s 切段、`buildWavHeader()` 补 WAV 头写临时文件后顺序播，
  沿用 `player.ts` 文件播放器）。`TTS_PLAYER` 对流式只在取值为已知流式 id 时生效；两条路径都无 → `selectAudioStrategy()` 同步抛错。
  `normalizeWavHeader` 保留（兼容/测试），流式路径不再使用。
- **打断（barge-in）**（新增 `src/voice/playback-state.ts`）：播放进程把 `{pid, provider, taskId, startedAt, kind}`
  原子写到 `<配置目录>/.tmp/data/emotions/tts-playback`；触发点 `src/emotions.ts` `chat.message`（用户发消息）与
  `src/tui.tsx` `toggleMode()`（`F8`/`F9`）。`stopPlayback()` 按 PID 先 `SIGTERM`、有界超时后 `SIGKILL`，
  仅当 `pid>1`、`pid≠自身`、未超 TTL(30min)；无记录/已退出/陈旧/损坏一律静默降级；被杀的播放进程发 `directive=cancel` 再退出。
  新播放启动前也先 `stopPlayback()`（打断上一条，取代「跨进程不保证」）。
- **增量自动朗读**（`src/voice/auto-read.ts` 重写）：监听 `message.part.updated`（`TextPart`），按 `part.text` 全量 +
  已送偏移取增量，`splitCompleteSentences()` 按句切；同一消息句子**串行队列**（`drain` 一次一句）派生 CLI `speak`；
  `message.updated` 建立 `messageID→role` 表**只读 assistant**，过滤 reasoning/非 text/synthetic/ignored；
  完成时补读未完片段并置 `seen`；未观察到 part 更新的消息**回退整段读**；`interrupt()` 清队列 + kill 当前子进程。

## 为什么
- 边收边播把「首包延迟」从「整段合成完成」降到「首句音频帧到达」。
- 用户发消息/开始语音输入时，旧语音仍继续朗读会干扰；需要**即时静音**且**跨进程**可控。
- auto_tts 不应等整条回复生成完；边生成边读更自然。

## 代价 / 存疑
- **auto_tts 不是单连接长会话**：受「插件进程 vs 分离播放进程」边界限制，采用**按句**派生 CLI（每句一次连接/进程），
  句内是流式、句间有连接开销；单连接长会话需常驻 `__stream` 守护进程（本轮未做，见设计文档 §15.4）。
- **Windows 无 stdin 播放器**（`ffmpeg-static` 不含 ffplay）→ 默认走**分段回退**，段间可能有轻微间隙；设
  `TTS_PLAYER=ffplay`（系统带 ffplay 时）可回到流式。
- **`cosyvoice-v2` 不支持 `instruction`**：配置了风格指令也会被忽略（记日志）；要用需换 v3/v3.5（注意音色版本须一致）。
- **打断窗口**：`stopPlayback` 后已入队未播的句子被丢弃（后续增量继续），未做「未播内容恢复」。
- 真机播放/打断（桌面 + Termux）由用户验证；本批单测覆盖消息构造/取消/chunk/策略与流式播放器选择/PID 状态与降级/增量去重。

# 变更说明（同日追加）：按标点断句 + 自实现 Windows 流式播放器（2026-10-15）

对应原文档：`docs/设计-语音输入注入.md` §15.1/§15.3/§15.4；`docs/ASYNC.md` 交互点 ⑩⑫与不变量；README「流式/音频落地/自动朗读/平台差异」。

## 原
- **切句三处口径不一致**：合成分块用 `aliyun.ts` 私有的 `splitBySentence()`（漏了英文 `.`）；自动朗读用 `auto-read.ts`
  的 `splitCompleteSentences()`（额外按 120 字硬切）；退化播放分段用**固定 1.5s 时长**切（与句无关）。
- **Windows 无流式播放器**：`stream-player.ts` 在 win32 只认 `ffplay`；`ffmpeg-static` 不含 ffplay → 实际总是走**分段回退**（固定时长切段，段间有间隙）。

## 现在
- **统一标点断句**：新增纯函数 `src/voice/tts/sentences.ts` `splitSentences()`——中/英句末标点（`.` 仅在**后接空白/结尾**时算句末，避免 `3.14`）、
  换行；标点**跟在前句末尾**、**连续标点并入同句**、空段丢弃；未以标点结尾的**尾巴**由 `tail` 原样返回（**只有遇到标点才算一句完成**）。
  - 合成分块：`chunkText()` 改用它（尾巴单独成段），**不再按字数切句**，仅单句超服务端上限（≤2 万）才硬切。
  - 自动朗读增量：`auto-read.ts` 改用它，**删除** `splitCompleteSentences`/`MAX_SENTENCE_CHARS`（不再 120 字硬切）；`AutoReaderDeps` 去掉 `maxSentenceChars`。
  - 退化播放分段：**段边界 = 句边界**。
- **Windows 内置 waveOut 流式播放器**（`stream-player.ts`，id `waveout`、别名 `winmm`；win32 首选，其次 `ffplay`）：
  `pwsh`/`powershell` + `Add-Type` 内联 C# 调 `winmm`（`waveOutOpen`/`PrepareHeader`/`Write`/`Reset`/`Close`），从 **stdin 读裸 PCM**、
  有界队列（≤8 个 `WAVEHDR`）边读边播、**连续无间隙**；EOF/`Ctrl+C` 先 `Reset`+`Close` 再退出。内联 C# 编译产物缓存到 `%TEMP%`（同运行时复用）。
- **AudioSink 新增 `boundary()`**：provider 在每句音频收完后调它落一段。分段路径改为**一句一会话**（每句 `run-task→…→finish-task`，收齐再落段）；
  `SegmentedSink` 去掉固定 1.5s 自动切段，保留安全上限 `MAX_SEGMENT_SECONDS`(30s) 兜底。
- **`platform.ts` 修复**：`isExecutableFile` 兼容 Windows 应用执行别名（`statSync` 抛 `EACCES` 的 `WindowsApps\pwsh.exe`），使 `pwsh` 能被探测并优先（启动 ~0.3s vs `powershell` ~1s）。

## 为什么
- 固定字数/字节切句会切断语义；按标点切句更自然，且「首句一出现句末标点即开始朗读」降低首句延迟。
- Windows 上没有任何现成 stdin 流式播放器（无 ffplay），必须自实现才能「边收边播、无间隙」。

## 代价 / 存疑
- **分段路径一句一会话**：多几次连接/会话开销，换精确句边界与更少段间间隙（仅在没有流式播放器时发生）。
- **内置播放器首次 `Add-Type` 编译**约 1s（之后同运行时缓存 DLL）；按句自动朗读每句各起一个播放进程，仍有 `pwsh` 启动开销（~0.3s/句）。
- **`.` 的缩写不特判**：`e.g. ` 会被当作句末（已知取舍；小数 `3.14` 已保护）。
- 真机听感（是否连续、首句是否很快出声）由用户验证；本批单测覆盖 `splitSentences` 全规则、内置播放器选择/脚本、`SegmentedSink` 段边界、`chunkText` 句边界一致。

# 变更说明（同日追加）：流式送文改「阈值 + 增量」+ 新增 `tts.streamMinChars`（2026-10-15）

对应原文档：`docs/设计-语音输入注入.md` §15.1/§15.3/§15.4；`docs/ASYNC.md` 交互点 ⑩⑫与不变量；README「流式 / 自动朗读 / 语音配置表」。

## 原
- **合成分块按句**：`chunkText()` 用 `splitSentences()` 按句末标点切句、再聚合到单条 ≤ `CONTINUE_CHUNK_CHARS`(200)，
  **第一句一出现句末标点才开始**送 `continue-task`。
- **自动朗读按句**：`auto-read.ts` 用 `splitSentences()` 切完整句，每句派生一次 CLI `speak`；未完尾巴留待后续增量。
- 阈值/缓冲概念**不存在**：开头只要成句就发 / 就读，且切分粒度绑死在标点上。

## 现在
- **新增纯函数** `src/voice/tts/stream.ts` `createStreamChunker({ minChars, maxChars })`（`push`/`flush`/`started`）：
  **不做句切分**，缓冲到 ≥ `minChars` 才首次发送、之后**随到随发**；`flush()` 结束兜底（含未达阈值的短文本）。
  单条上限 `MAX_CONTINUE_CHARS`(2 万)、累计上限 `MAX_TOTAL_CHARS`(20 万) 迁至 `stream.ts`（服务端约束不变）；
  **删除** `chunkText` 与 `CONTINUE_CHUNK_CHARS`。
- **流式合成**（`aliyun.ts` `runStream()`）：改用 `createStreamChunker({ minChars: tts.streamMinChars })`，
  **不再按句分块**；正常路径一块送出（超上限才硬切）。
- **自动朗读**（`auto-read.ts`）：改用同一分块器——**缓冲到 `tts.streamMinChars` 才首次派生 CLI，之后逐增量各派生一次**；
  完成时 `flush()` 补读未达阈值的缓冲；`AutoReaderDeps` 新增 `streamMinChars`（缺省读 `emotions.jsonc` 的 `tts.streamMinChars`）。
- **新增配置 `tts.streamMinChars`**（默认 **5**，非负整数；env `TTS_STREAM_MIN_CHARS`）：`VoiceConfig.tts`、`DEFAULT_VOICE_CONFIG`、
  配置模板、`TtsFileDefaults`/`ResolvedTtsOptions`/`resolveTtsConfig`、README 配置表、`--help`、`status` 全部同步；
  负/非数字归一（负→0、NaN→默认）。
- **`splitSentences()` 保留但收窄**：**仅**用于无流式播放器时的**退化分段**（`runSegmented()` 的段边界），
  **不再**用于合成分块或 auto_tts 主切分。

## 为什么
- **真流式无需按句**：CosyVoice 服务端本身会自动分句流式合成；客户端按句切反而把发送时机绑死到标点，
  遇到无标点长段会长时间不发声。改为「阈值 + 增量」后，文本一到阈值即开始、之后随到随发，更顺滑。
- **阈值防开头卡顿**：开头往往只有一两个字（如「好」「嗯」），立刻建连/送文既浪费又易造成开头卡顿；
  缓冲到 `streamMinChars`（默认 5）再发，兼顾「开头不卡」与「不拖延」。

## 代价 / 存疑
- **阈值只在真增量源（auto-read）可观测**：CLI `speak` 路径一次性拿到完整正文，`createStreamChunker` 对其
  等价于「按上限硬切」（短于阈值时由 `flush()` 兜底）；真正体现阈值的是 auto-read 的逐增量转发。
- **每增量一次 CLI**：auto-read 已开始后每个增量各派生一次 `speak`（原按句派生），进程/连接开销随增量数上升；
  受 `drain` 串行队列约束，同一时刻只播一块（不做合并——保持「随到随发」语义）。
- 真机听感（开头是否更流畅、有无碎句）由用户验证；本批单测覆盖 `createStreamChunker` 阈值/硬切/flush、
  `resolveTtsConfig`/`loadVoiceConfig` 的 `streamMinChars`、以及 auto-read 的「未达标不读 / 达标开始 / 逐增量」。
