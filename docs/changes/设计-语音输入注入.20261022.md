# 变更说明：语音运行时脚本改按**插件产物自身位置**解析（2026-10-22）

对应原文档：`docs/设计-语音输入注入.md` §4 运行时 / §5 时序；`docs/ASYNC.md` 交互点 ⑥与不变量「至多一个存活子进程」段；`README.md`「产物镜像」段。
改动 `src/tui.tsx`、新增 `src/lib/runtime-diagnostics.ts`、新增 `test/runtime-diagnostics.test.js`、补 `test/tui-diagnostics.test.js` 产物锚点断言。

## 现象（用户实测）
在家目录 `C:\Users\king-\` 启动 opencode，按 F8/F9 起不来，toast：
`语音运行时已退出（code=1 signal=-）；stderr：Node.js v24.16.0`。
日志：`mode started` 后约 1s `childAlive=false`。

## 根因
`src/tui.tsx` 旧代码 `const script = process.env[SCRIPT_ENV] || resolve(process.cwd(), ...RUNTIME_SCRIPT)`
——运行时脚本按 **cwd 相对**拼。插件产物在 `~/.cache/opencode/packages/.../dist/`，cwd 却是用户启动目录
⇒ 拼出 `C:\Users\king-\dist\runtime\voice-runtime.js`（实测不存在）⇒ spawn 的 node `Cannot find module` 立即退出。
次生问题：stderr 只留**末行**，而 Node 崩溃输出末行是版本横幅 ⇒ 提示里只剩 `Node.js v24.16.0`，看不出原因。

## 原来 → 现在
- **脚本路径口径**：原来 `VOICE_RUNTIME_SCRIPT` > `<cwd>/dist/runtime/voice-runtime.js`（唯一口径）。
  现在 `VOICE_RUNTIME_SCRIPT`（显式覆盖，最优先，相对值按 cwd 归一）> **插件产物自身位置**
  （`SELF_DIR = selfDirFromModuleUrl(import.meta.url)` → 同级 `runtime/voice-runtime.js`）> cwd 拼法（**仅兜底**，
  日志以 `scriptSource=cwd` 显式标注）。`dist/` 与镜像后 `.opencode/plugin/` 两种布局同构，同一锚点都命中。
  - 锚点选择依据：TUI 产物是 ESM，`scripts/build-tui.mjs` 的 Babel 链（`babel-preset-solid` + `preset-typescript`，
    无模块转换预设）**原样保留 `import.meta.url`**（已实测：`dist/tui.js:97` 存在该表达式，且有产物文本断言防回归）。
    宿主若把模块 URL 虚拟化（非 `file:` / 非绝对路径），`selfDirFromModuleUrl` 返回 `null` ⇒ 自动降级兜底并记日志。
- **不再依赖 cwd，也不静默**：候选都不存在 ⇒ `startRuntime()` 在 spawn **之前**抛错，错误与 `startRuntime begin`
  日志都带**完整绝对路径 + 来源 + 全部候选**（`scriptSource=` / `scriptExists=` / `selfDir=` / `candidates=`）。
- **stderr 口径**：原来 toast 显末行（截 24 字符）。现在 toast 显**关键行**（`pickStderrSummary`：优先含错误标记的行
  → 首个非噪声行 → 首行，截 120 字符），进程内 `stderrTail` 留末尾 4000 字符、折叠换行进 `runtime exited:` /
  `startRuntime failed:` 日志（全量可还原）。
- **影响面**：`VOICE_RUNTIME_SCRIPT` 语义不变（仍最高优先）；未设该 env 的用户由「cwd 口径」改「产物口径」——
  属修复，无需迁移。旧常量 `RUNTIME_SCRIPT`（cwd 路径段）移入 `lib/runtime-diagnostics.ts` 的
  `RUNTIME_RELATIVE_TO_CWD`，`tui.tsx` 不再自行拼路径。

## 验证
- 新增/补强单测 15 例（247 → 262，全绿）：路径解析四态（env/self/cwd/none）、镜像布局、锚点不可靠降级、
  stderr 关键行与截断；`test/tui-diagnostics.test.js` 断言产物含锚点且旧 cwd 拼法不复活。
- 静态端到端探针（cwd 设为家目录复现根因）：解析得 `<repo>/dist/runtime/voice-runtime.js`，
  `source=self exists=true`；旧口径 `<home>/dist/runtime/voice-runtime.js` 实测不存在。
- 待真机确认（由用户）：重启 opencode 后在家目录按 F8/F9，日志应出现 `startRuntime begin: … scriptSource=self`。

# 追加（同日第六批）：会话级中断请求水位 `interrupt-req`——修「按 F10 中断后剩余文本继续播」

对应原文档：`docs/设计-语音输入注入.md` §14.2（共享状态清单）、§15.2（触发点③/新增「会话级中断请求水位」条/F8·F9 正确性链路的**边界收窄**）、§15.3（新增「打断的第二条入口」）、§16.4（门释放姿势）；`docs/ASYNC.md` 并发边界清单增 ⑰、交互点新增 ⑰、不变量新增「会话级中断请求水位」。
改动 `src/voice/auto-tts.ts`（`INTERRUPT_REQ_FILE_NAME`/`autoTtsInterruptPath`/`writeInterruptRequest`/`readInterruptRequest`）、`src/tui.tsx`（两处中断出口写水位）、`src/voice/auto-read.ts`（`messageStarts` 记账 + `stopInFlight` 抽取 + `applyInterruptRequest` 消费）；测试 `test/auto-tts.test.js` +8、`test/tui-diagnostics.test.js` +1。

- **现象（用户实测）**：按 F10 中断播放后，**有时**剩余文本继续播、有时正常。
- **根因（不是概率，是结构缺口）**：F10 的中断动作只有 `stopPlayback({ sessionID })`（按 `tts-playback` 里的 PID 杀进程），而服务端 auto-read 对「用户按了中断」**一无所知**。两个缺口：① **杀空**——按键落在两个朗读单元之间（上一句已播完、下一句还没投递），此刻没有登记在册的播放进程，`stopPlayback` 无事可杀，队列里的下一句照旧 `spawn`；② **杀后重生**——follow worker 被杀后该消息改走 `deliverUnit` 的**非 follow 分支**重新 `spawn` CLI。§15.2 原结论「F8/F9 中断链路真实存在、**无缺口**」只覆盖「已有进程被杀中且后续确实写失败」这一条，本批**收窄该结论**并补上兜底（链路本身未改）。
- **原来 → 现在**：原来中断意图只活在 TUI 那一次 `stopPlayback` 调用里；现在**先原子写** `<会话目录>/interrupt-req`（内容=请求时刻）**再** `stopPlayback`——写序保证停播抛异常时意图也已落盘。消费端在**每个派发单元前同步读一次、不加缓存**（`deliverUnit` 入口=follow 写前=非 follow spawn 前的唯一派生入口；`runFallback` 整段读前补一处），要的正是新鲜度（单元间隔秒级）。
- **命中语义（钉死）**：请求时刻**严格大于**该消息开始时间 ⇒ 命中 ⇒ 走与 `interrupt()` **同一套**打断执行体（`interrupt()` 的函数体抽成 `stopInFlight(sessionID?, startedBefore?)`，`interrupt` 只是不带时间上限的调用——**没有第二份水位/清队列/杀进程代码**）：置 `interrupted` 水位＋清队列/carry＋按归属只 kill 本会话且开始早于水位的子进程。水位是**会话级时间戳**不是布尔 ⇒ 晚于水位的**新**消息不受影响（F10 双态只停声、开关没变 ⇒ 后续回复照读）；**相等不算命中**。
- **开始时间从哪来**：新增 `messageStarts`（`messageID→开始时间`，上限 `MESSAGE_START_LIMIT`=200）——优先服务端 `info.time.created`（权威、早于插件观察，晚到事件可覆盖），否则 `diagFor` 建计数条目时的首次观察时刻。**无记账 / 读失败 / 缺文件 / 内容非法**一律**放行**（宁可漏拦不可误杀，绝不影响热键与朗读主链）。
- **不改**：F10 双态语义（中断分支**不写**开关文件、不 bump 指示灯）、i18n toast、runtime、CLI、`playback-state` 的 `stopPlayback` 本身。F8/F9 写水位带「取到会话路由才写」门（取不到不写，保持无主语义）；F10「关闭」分支仍只写开关文件（`drain` 派生前实时复查已覆盖），**不**写水位。
- **清理口径**：`interrupt-req` 在**会话目录内** ⇒ 随 `resetAutoTtsSession()`/`resetAutoTtsState()` 整目录删除一起清；**不进** `AUTO_TTS_RESET_KEEP_NAMES`（那个清单只管 base 根的 `tts-playback`/`tts`，误加会把水位文件当保留项留下）。
- **残余（已知、不掩盖）**：已递给 worker/CLI 的**当前单元**不追回（靠 `stopPlayback` 双 PID 静音），生效延迟只到下一个单元；插件从未观察到的消息无开始时间记账 ⇒ 不被水位命中（与交互点 ⑫ 的既有残余同源）。

# 追加（同日第十三批）：句间停顿优化·修法 1（音频首尾静音裁剪 + 首句合并窗）

> 依据：`.tmp/scratch/gap-analysis.md` 实测——句间主观停顿 ≈2.0~2.3s = 每单元管线重启 ≈1.7s
> （CLI 冷启动 0.30 + 合成 TTFB 0.64~0.78 + 播放器就绪 0.57 + 收尾）+ TTS 自带首尾静音 0.5~0.65s。
> 本批只做「首尾静音裁剪 + 首句合并窗」两项低风险修法；预取 / 常驻 worker 留后续批次。

## 1. 音频首尾静音裁剪（`src/voice/tts/silence-trim.ts` 新增 + `audio-sink.ts` 接线）

- **原行为**：provider 收到的 PCM 原样写播放器（或落成 WAV 段）——云端 TTS 自带的
  首部静音 0.09~0.14s、尾部静音 0.36~0.53s 全部被播放，逐单元串行时直接叠加进句间停顿。
- **根因**：`AudioSink` 只做「接收 → 转交」，没有任何能量判定；首尾静音属于 TTS 输出的一部分，不是播放链路问题。
- **现行为**：新增纯逻辑 `SilenceTrimmer`（`tts/silence-trim.ts`，无 IO、可单测），两条播放路径统一接入：
  - 能量口径**复用** `src/voice/level.ts`（新抽，`pcmRms` + `rmsToDbfs`；`asr/segment.ts` 改为引用并再导出，
    ASR 行为与 API 不变），按 **10ms 短帧**结算，帧边界与 chunk 边界无关；
  - 门限 `TTS_TRIM_THRESHOLD_DBFS = -45`（RMS≈0.0056，留约 10dB 语声余量）、
    尾部保护余量 `TTS_TRIM_TAIL_GUARD_MS = 100`、尾部静音暂存上限 `TTS_TRIM_TAIL_HOLD_MAX_MS = 800`、
    首部静音暂存上限 `TTS_TRIM_LEADING_HOLD_MAX_MS = 2000`（超过即放弃首部裁剪、原样放行）；
  - **首部**丢弃到首个有声帧为止（只丢字节，**不增加首音延迟**）；**尾部**只保留最后 100ms，其余丢弃；
    句内停顿遇到后续有声帧整体放行（不改语流）；**全静音流原样放行**（绝不裁成空）；
  - 字节按 2 字节采样点对齐（chunk 奇数字节跨块拼接，流尾单个残字节丢弃）；
  - 流式路径 `StreamSink` 首个**有声**帧才 spawn 播放器；分段路径 `SegmentedSink` 每句一个裁剪器，
    `boundary()` 结算并累计统计；`AudioSink.trimStats()` 暴露裁剪时长（观测/自测用）。
- **实测（真实 `createAudioSink` 流式路径 + 假播放器计 stdin 字节，`.tmp/scratch/trim-e2e.mjs`）**：
  unit1（24 字，MiMo 总 4.80s）**4.80s → 4.45s**（首裁 90ms / 尾裁 260ms，省 0.35s）；
  unit2（37 字，总 7.36s）**7.36s → 6.80s**（首裁 140ms / 尾裁 420ms，省 0.56s）。
- **口径冲突（如实记录）**：任务里「缓冲 ≤150ms」与「裁掉 0.36~0.53s 尾静音」物理上不可同时成立
  （暂存多久才能裁多久）。这里选**目标**：只暂存**静音帧**、上限 800ms，超出即放行最旧整帧
  （正常 TTS 单句内不会出现 >800ms 停顿，语声时序零影响）；若坚持 150ms 上限，尾静音最多只能裁 50ms。

## 2. 首句合并窗（`src/voice/auto-read.ts` `drain`）

- **原行为**：`drain` **无时间阈值**——第一个完整句一到立即 `deliverUnit`。61 字回复被切成 24 + 37 两个单元，
  单元 1 播完后为 37 字再重启一次整条管线（实测 ≈1.7s）。
- **现行为**：每消息**首个**派发单元就绪、消息流未结束、且本批恰好只有 1 个完整句单元时，最多等待
  `FIRST_MERGE_WINDOW_MS`（默认 **400ms**，范围 `[0,1500]`，`normalizeFirstMergeWindow` 夹取；0=关闭）：
  > 第十五批已改为**自适应合并窗**（基值 400ms、上限 1200ms、下一条到达即合并），上述 `[0,1500]` 固定窗为当时口径。
  - 窗口到期或**流在窗口内结束**（`finalize()` 主动唤醒 `wakeFirstWindow("done")`）⇒ 立即派发；
  - 窗口内新完成的**完整句**在结算时按 `splitDrainUnits()` 口径并入首单元（沿用 2000 字上限与 carry 语义，
    句对齐/顺序不变；超上限的完整句按原顺序作为本批后续单元）；
  - 第 2 个及以后单元**不等待**（`firstDispatchDone` 已置位）；首单元即最后一句（流已结束）也不等待；
  - **打断优先级最高**：等待期间消息级 `interrupt()`（同进程 `wakeFirstWindow("cancel")`）、
    会话级 `interrupt-req`（50ms `FIRST_MERGE_WINDOW_POLL_MS` 复查 + `applyInterruptRequest`）、
    F10 关闭开关、子会话门任一命中 ⇒ **立即取消等待、不派发**并清空待读文本（绝不因合并窗拖延中断）。
- **代价**：首音延迟最多 **+400ms**；短消息且首句即末句时不会白等；可设 0 恢复旧行为。
  （第十五批已改为**自适应合并窗**：基值 400ms、上限 1200ms、下一条到达即合并，首音延迟上限随之为 +1200ms。）

# 第十四批（句间停顿优化·预取）

## 1. 问题与根因（沿用 gap-analysis 实测）

- 每个朗读单元 = 新 CLI 进程（冷启动 0.30s + MiMo TTFB 0.78s + 播放器就绪 0.57s ≈ **1.65s**）+ 播放时长；
  单句播放 2~3s > 合成 1.6s ⇒ 上一句播完后，下一句才开始**合成**，用户听到约 1.5~1.7s 的管线重启空档。
- 前两批（静音裁剪、首句合并窗）只减少**重启次数**与静音，不改变「合成在播放之后」这一串行关系。

## 2. 现行为：播 N 时预取 N+1（深度 1）

- **只合成不出声**：新增 CLI `speak --text-file … --pcm-out <wav>`。provider 合成链路完全复用（`sinkFactory`
  注入 `PcmFileSink`），16bit PCM 以 WAV 容器落盘；**不播、不登记 `tts-playback`**。
- **预热播放器**：合成成功后派生 `speak --pcm-file <wav> --await-go`；`StreamSink.prewarm()` 提前 spawn
  播放器（waveOut 打开设备后在 stdin `Read` 上阻塞 ⇒ 无声），等父进程写 `go`。
- **交播**：第 N 句的 CLI 进程退出（= 音频放完）后，父进程写 `go\n` 并关 stdin；N+1 进程随即流式写音频。
  交播点才登记 `tts-playback` 并打印 `OC_PCM_PLAY_STARTED`（用于区分「从未起播」与「播完/播中失败」）。
- **队列所有权**：预取只在该消息**已有单元在播**时启动；候选 = `carry + queue` 的第一个完整句单元，
  用**原文偏移**（`splitSentenceSpans`/`splitDrainUnitSpans`）从队列摘走，顺序确定、句间空白不错位。
  单槽（深度 1）；同批多单元时直接预取 `batchUnits[i+1]`。
- **打断即弃**：`interrupt` / 新消息 / F10 / `interrupt-req` / 子会话门 / `dispose` 任一命中 →
  `discardPrefetch()` kill 合成与预热子进程、删缓冲；交播前再查一次 `interrupt-req` 水位。
- **失败降级**：合成失败/超时/超上限/播放器从未起播 → `entry.play()` 返回 false → 用 `entry.text`
  退回串行 `deliverUnit`（不丢句）；已出声后异常退出不重读（避免重复）。
- **内存有界**：`PcmFileSink` data 区上限 = `min(32MB, 采样率×2×120s)`，超限失败并删除半成品。
- **首句不变**：第 1 句仍走原直播流路径，不增加首音延迟；预取只在它**开始播放后**启动。

## 3. 实测（`.tmp/scratch/prefetch-e2e.mjs`，假 CLI：合成 1.6s / 播放 3s / 预热 0.57s）

|---|---|---|
| 预取开 | **13ms**（三轮 10–13ms） | 目标 <200ms 达成 |
| 预取关（对照） | **1722ms**（三轮 1700–1753ms） | 与现状一致（CLI 冷启动 + 合成） |
| 预取中打断 | 交播 spawn=0、play-start=0、存活旧 PID=[] | 无残留播放/孤儿进程 |
| 预取失败 | 第 2 句仍完整播出（串行 1733ms） | 降级不丢句 |

## 5. 残余风险（如实）

- **资源占用**：稳态最多 1 个在播 + 1 个预取合成 + 1 个预热播放进程（都是 node CLI）≈ 3 个 Node 进程；
  CPU 主要花在 base64 解码/网络，内存按单元 PCM 上限（≤32MB）**落盘**而非常驻。低配机器上并发合成
  仍会与当前播放争 CPU（播放本身几乎不吃 CPU），未做节流；可用 `TTS_PREFETCH_DEPTH=0` 关闭。
- **provider 单实例约束**：预取走**独立 CLI 进程**（provider 实例各自一份），不需要放宽 provider 单例；
  server 插件进程仍不持有说话中的实例。代价是每单元多一次 node 冷启动（已被「提前 1 句」掩盖）。
- **打断竞态残余**：F10/新消息到达时若恰好处于「N 已退出、N+1 刚拿到 go」的微秒级窗口，N+1 可能已写出
  首帧；此后 `tts-playback` 已登记，TUI 的 `stopPlayback` 会杀掉它（不会继续播完整句）。已交播的播放进程
  被杀后，waveOut 已排队的 ≈160ms 仍会播完（既有语义）。
- **预热占用音频设备**：预取进程会提前打开 waveOut（无声）。独占模式下预热可能失败；失败后退化为
  「首帧才 spawn」（仍比串行快，但失去 0.57s 预热收益）。
- **磁盘临时文件**：正常播完/失败/打断即删；Windows 播放器仍持有句柄时删除可能失败，残留到系统临时目录清理。

## 第十五批（2026-10-23，预取改边合成边交播）

- **问题**：预取要等整段合成完才交播。105 字的长单元合成 6s > 前一句播放 3s ⇒「解渴。」播完后仍停 4s（日志 08:54:58 两段 + 08:55:02 一段）。
- **改法**：原来「合成完 → 预热 → 等 `go` 交播」，现在 `speak --pcm-file --pcm-follow` 跟随增长读取（交播即播已到达部分，写端 `done`/`abort`/EOF 收尾）；预热移到 `go` 之前（仅开设备、不出声、不登记 `tts-playback`）；`PcmFileSink` 原 `min(32MB, 120s)` 截断改为写盘不限、播完即删。
- **防双播**：原来靠「是否写过音频」推断出声，现在判定「是否已出声」改用退出码——`0`（播完）/`3`（已播部分后写端异常）绝不重读；仅 `1`（从未起播）才重试一次；未知退出码/被取消按已播处理（宁可漏播不重播）。
- **合并窗**：原来固定 400ms，现在自适应（按观测到的句间到达间隔放宽、上限 1200ms、下一条到达即 `arrived` 合并）；本例 16/17 字两段现已合并为一次派发。
- **实测**：句间空档 3622–3665ms → 3–14ms；静音裁剪 6800ms → 6100ms；abort 场景退出码 3、0 次重读。
- **残余风险**：合成与播放在同一磁盘上并发读写（15ms 轮询），写端卡顿会让播放抖动；F10 落在「上一句退出、下一句刚起播」的微窗仍可能已出声。
