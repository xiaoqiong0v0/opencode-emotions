# 语音输入 + 情绪 → 注入 opencode 设计（v0.3，单 TUI 插件）

> 状态：待评审 ｜ 日期：2026-10-13
> **硬约束：全链路 TypeScript / Node，不依赖 Python**（不是每台机器都装了 Python）。
> v0.1（含 Python 采集侧）与 v0.2（server 插件 + HTTP 网关 + session-tracker + process-manager）作废；
> 改为**单个 TUI 插件**（`src/tui.tsx`）承担全部：UI + 热键 + 运行时管理 + 分发。

## 1. 目标

- 说一句话 → 转写 + 情绪识别 → **注入当前 opencode 会话**（等同用户发了一条消息）
- 情绪归一为既有标注 **`emoji(等级/3)`**（与手动来源统一）
- **去掉手动符号解析**（`!`/`?`/`...`/`...`/`666`），**保留命令**（`/angry` 等）作手动兜底
  （**已实施**：`emotions` 插件不再解析/改写消息，仅注册命令 + 清理标注尾部空白，见 `docs/设计-情绪输入插件.md`）
- 提供一个**可交互的 UI**：开始/停止连续语音、看到状态、可切换会话

## 2. UI 能力调研（关键结论）

opencode **有一套 TUI 插件系统**（`@opencode-ai/plugin/tui`，本机 `dist/tui.d.ts` 取证），**但官方文档完全未写**。

**可用能力**（`tui.d.ts`）：
| 能力 | API | 用途 |
|---|---|---|
| 槽位（常驻 UI） | `api.slots.register({ order, slots })`；`TuiHostSlotMap` = `app` / `app_bottom` / `home_prompt(_right)` / `session_prompt(_right)` / `session_sidebar_(title\|content\|footer)` … | 在界面固定位置渲染（如把「麦克风按钮/指示灯」放到输入框右侧 `session_prompt_right`） |
| 快捷键 | `api.keymap.registerLayer({ commands, bindings })` | 注册热键（如 `ctrl+r` 开始/停止） |
| 路由/会话 | `api.route.navigate(name, params)`、`api.route.current`；`session.get(...)` | **切换会话** |
| 写入输入框 | `api.prompt.set(TuiPromptInfo)` / 事件 `tui.prompt.append` | 把识别结果**填进输入框**（而非直接发送） |
| 提示 | `api.ui.toast(...)` / `api.ui.notify(...)` | 状态提示 |
| 整页路由 | `api.route.register([{name, render}])` | 独立页面（可选） |

**约束与风险**：渲染是 **SolidJS**（`SolidPlugin`）；**无文档、跨版本可能变**；装载需 `exports["./tui"]` 或 `{id, tui}` 导出。

**Web UI / `opencode serve` 不可扩展**（固定 OpenAPI 前端）。

## 3. UI 方案（**已定：A · TUI 槽位**）

- **决定：A（TUI 槽位）**。理由：`/voice` 这类**命令本质是「注入提示词 → 由模型调用工具」**，**有延迟且不可控**（还要等一个模型回合）；要做到「点击即开始/停止、实时状态」必须是**原生 UI**。
- **单插件**：全部落在 `src/tui.tsx`（`export default { id, tui }`）。**不再需要 server 插件**——spike 已证实 TUI 插件自带 `api.client`（`OpencodeClient`），可直接 `session.prompt` 注入、`tui.appendPrompt` 写输入框。

## 4. 全 TS 架构

```
麦克风 ─► [Node 采集] 16k 单声道 PCM 分片
        ─► [Node ASR 客户端] 阿里云实时（WebSocket / 官方 Node SDK）
              └─ 得到 { text, emotion }
        ─► 情绪映射 → emoji(等级/3)
        ─► [opencode TUI 插件] 注入 / 填输入框 / 显示状态
```

### 4.1 麦克风采集（Node）—— **已验通**
- **选定方案**：`ffmpeg-static`（npm 自带预编译 ffmpeg）+ `spawn` 取裸 PCM。
  - 命令：`-f dshow -i audio="<设备名>" -f s16le -ar 16000 -ac 1 -`（Win；mac `avfoundation`、Linux `alsa`）
  - 本机 spike：**采到真实 PCM 帧（非 0）** → 链路成立
- **存储代价**：`ffmpeg.exe` ≈ **79MB** → **不建议随包分发**；改为**运行时按需下载**，或用环境变量 `FFMPEG_BIN` 指定用户自备路径。
- ⚠️ 本机 spike 电平≈静音（RMS≈0.0004）→ 疑似**麦克风被静音/增益 0**，需人工确认真能采到人声。
- 备选：Node 原生音频模块（PortAudio 绑定）——本项目不采用。

### 4.2 ASR（Node）
- **云（阿里云百炼）**：官方有 Node SDK / 或直接 `ws` 实现协议（已有协议细节）：
  - `paraformer-realtime-v2`（无情绪）、`paraformer-realtime-8k-v2`（3 类情绪，仅 8k）、`qwen3-asr-flash-realtime`（7 类情绪，16k）——**推荐 qwen3**（情绪最细）
  - 端点 `wss://{workspaceid}.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference`（或 `/realtime?model=qwen3-asr-flash-realtime`），头 `Authorization: Bearer <apikey>`
- **本地（可选）**：sherpa-onnx 有 Node 绑定（`sherpa-onnx-node`，**需核实**）——有则可保留本地引擎，否则本地引擎暂缓。

### 4.3 情绪 → 标注

### 4.4 注入 / 写输入框（单 TUI 插件，`api.client`）
TUI 插件自带 `api.client`，故**无需 server 插件**。两种模式（互斥，热键切换）：

- **模式 A（语音注入，`F9`）** → 变成新消息，带 `🎙` 标记：
  ```
  api.client.session.prompt({
    sessionID,                       // 取自 api.route.current.params.sessionID
    noReply: false,
    parts: [{ type: "text", text: `🎙 ${annotation ? annotation + " " : ""}${text}` }],
  })
  ```
- **模式 B（语音输入，`F8`）** → 增量追加进主输入框，不覆盖用户已输入内容（spike A 已验证）：
  ```
  api.client.tui.appendPrompt({ text: ` ${annotation ? annotation + " " : ""}${text} ` })
  // 等价备用：api.client.tui.publish({ body: { type: "tui.prompt.append", properties: { text } } })
  ```

> **API 形态注意**：`api.client` 是 **v2** `OpencodeClient`（`@opencode-ai/sdk/v2`），
> 其签名是**扁平的** `session.prompt({ sessionID, parts, noReply })`、`tui.appendPrompt({ text })`；
> 旧的 v1 形态 `{ path: { id }, body: { … } }` 属已删除的 server 插件（`client` 为 v1）。
> 依据：spike 的 `api.client.tui.appendPrompt({ text })`（扁平）实测成功（v1 要求 `{ body: { text } }`）。

- **运行时**：插件 `child_process.spawn` 起 `dist/runtime/voice-runtime.js --json`，逐行读其 stdout 的 NDJSON
  （契约见 `src/voice/ndjson.ts`：`ready` / `final` / `level` / `error` / `done`），按当前模式分发。
- **就绪反馈闭环（2026-10-22 缺陷一）**：runtime 是 **`connect()` 成功后才 `beginCapture`**（`voice-runtime.ts` 先 `ASR 已连接` → `emit ready` → 之后才采集），
  故「按 F8 到真正开麦」有 **1~3s 死区**（spawn node + WS 握手）；`startRuntime` 只等 `spawn` 事件、**不等 ASR ready**，若按旧 `busy` 信号点亮 `🎙` 则 toast「已开启（正在监听）」出现时其实还没开麦、且叠加 VAD 句尾静音默认 800ms ⇒ 用户「好几秒没反应」。
  **改法（不改架构、只做反馈闭环）**：TUI 新增 **`asrReady` 信号** —— runtime NDJSON `ready` 事件到达置真；`startRuntime`/`stopRuntime`/`handleChildGone`/关模式置假。
  meter 段据此三态化（关=`idle` 空白 / 开但未就绪=`connecting` 盲文 spinner / 开且就绪=`listening` 盲文电平条），用户在看到 spinner 时知道「还在连、别急着说」、看到电平条跳动时开口；
  `ready` toast 文案本就含「开始说话」/「Start speaking」（`i18n` `toast.ready`）⇒ **未改动**，与三态状态机协同消除死区困惑。
  **（第十三批修订）**：该三态**不再由 emoji 字形表达**（原 `⏳` / `🎙`↔`🎤` 帧动画已删，理由见 §3），`asrReady` 信号本身与置真/置假触点**保持不变**。
- **麦克风电平上行（`level` 事件，2026-10-22 第十三批）**：`runMic()` 在**采集激活期间**另起一个 `LEVEL_EVENT_INTERVAL_MS`（=100ms ⇒ **10Hz 节流**）的定时器，
  按「自上次上报以来的窗口」结算 PCM 的 RMS（`sumOfSquares`/采样数；**不是自采集开始的累计平均**，否则电平不会回落），
  经纯函数 **`rmsToLevel`**（`src/voice/meter.ts`；`level = rms / LEVEL_FULL_SCALE_RMS`，**满量程常量 0.08** 依据实测语音 RMS 约 0.01~0.06，超界 clamp 到 1、NaN/负/非有限 → 0）
  归一后发 `{ type: "level", level }`。
  **只在采集期间发**（`waitForStop` 返回即停表，`done` 之后不再发）；**尽力而为、可丢弃**——写 stdout 包 `try/catch`，失败或未 flush 只丢这一帧，绝不打断采集与识别。
  TUI 侧 `case "level"` **直接覆盖** `micLevel` 信号（不累积、不过滤，越界由 `slot.ts` 的 `meterGlyph` 归档）；
  因是 10Hz 高频事件 ⇒ **不 toast、不写日志**（本项目 logger 无 debug 级，逐条 info 会刷屏）。
  并发契约登记见 `docs/ASYNC.md` 交互点 ⑱。
- **运行时脚本路径口径（2026-10-22 根因修复）**：`VOICE_RUNTIME_SCRIPT` 覆盖 > **插件产物自身位置**（`import.meta.url`
  → `dist/tui.js` 所在目录 → 同级 `runtime/voice-runtime.js`；`dist/` 与镜像后 `.opencode/plugin/` 同构）> `<cwd>/dist/runtime/…`（兜底，日志标 `scriptSource=cwd`）。
  纯逻辑在 `src/lib/runtime-diagnostics.ts`（`selfDirFromModuleUrl` / `resolveRuntimeScript`，可注入存在性检查、可单测）；
  **候选都不存在 ⇒ 直接抛错并带完整绝对路径 + 全部候选**，不再 spawn 必死的 node 进程。
  旧口径只按 `process.cwd()` 拼 ⇒ 家目录启动 opencode 时 runtime 秒退（code=1），且 toast 只显 stderr 末行（`Node.js v24.x`）无从定位。
- **stderr 可见性**：toast 取**关键行**（`pickStderrSummary`：优先含错误标记的行 → 首个非噪声行 → 首行，上限 120 字符）；
  全量尾部缓冲（末 4000 字符）折叠成单行进 `runtime exited:` / `startRuntime failed:` 日志。
- **会话 id**：TUI 侧取 `api.route.current`（`{ name:"session", params:{ sessionID } }`）；不在会话路由时提示并忽略。
- 旧方案（2026-10-13 上午）：server 插件在 `127.0.0.1:8799` 起 HTTP 网关、TUI 经 `/start`·`/stop`·`/status` 控制、
> 运行时 POST `/inject`。**已删除**（server 与 TUI 是两个进程，属多余的一跳）。

## 5. 数据流 / 时序（连续对话）
1. 按热键（`F8` 输入 / `F9` 注入）→ 插件 `spawn` `dist/runtime/voice-runtime.js --json`（互斥，仅一个运行时）→ 槽位指示亮起；
2. 运行时 stdout 每行一个 NDJSON 事件 → 插件按行解析；`final` 时按当前模式分发（A 注入 / B 追加）；
   `level`（10Hz 节流）只更新槽位 meter 电平、不进分发链；`ready` 只置 `asrReady`；
3. 再按同键关闭该模式；若两模式都关 → `kill` 子进程、指示熄灭；
4. 子进程异常退出 → 插件复位开关、toast 提示，可按热键重启（不留孤儿进程：`api.lifecycle.onDispose` 会停止它）。

### 11.1 凭证（`asr.credentials` / `tts.credentials`，`src/voice/credentials.ts`）

- **优先级（逐字段合并，两侧各自独立）**：
  `DASHSCOPE_API_KEY`/`DASHSCOPE_WORKSPACE_ID`（环境变量） > 该侧 `credentials.apiKey`/`workspaceId`（配置直填）
  > 凭证文件（1 行 workspaceid / 2 行 apikey） > 默认 `<cwd>/.tmp/aliyun`。
- **文件路径**优先级：CLI `--credentials` > `VOICE_ALIYUN_CREDENTIALS`（兼容 `ALIYUN_CREDENTIALS`）
  > 该侧 `credentials.path` > 默认路径。
- **安全**：凭证只读、绝不打印；错误文本统一经 `redact()` 脱敏；缺字段抛清晰错误（信息不含密钥）。
- **两侧独立**：`asr.credentials` 只供 ASR、`tts.credentials` 只供 TTS，互不影响；只想用 TTS 时配 `tts.credentials`
  （或留空靠环境变量/默认文件）即可，不再被 ASR 配置绑住。`resolveCredentials` 是无状态的按次解析，
  调用方各传自己那一份 `credentials`。
- **MiMo 凭证两侧独立**（2026-10-20 拆分）：`asr.mimoCredentials.apiKey`（仅 mimo ASR）与
  `tts.mimoCredentials.apiKey`（仅 mimo TTS）各自独立，均为 env `MIMO_API_KEY` > 该组 `apiKey`、无 workspace；
  `resolveMimoApiKey` 通用，错误文案按调用方 `configPath` 提示对应路径（ASR 报 `asr.mimoCredentials.apiKey`、
  TTS 报 `tts.mimoCredentials.apiKey`）。此前 ASR mimo 误读 `tts.mimoCredentials`（违反「asr/tts 凭证各自独立」），已修。

### 11.2 ASR 语种/语料（`src/voice/config.ts` `resolveAsrParams` + `src/voice/aliyun.ts` `buildRunTask`）

- `asr.languageHints`（list）→ paraformer `parameters.language_hints`（显式优先，否则由 `asr.language` 推导）；
  仅 `aliyun-8k`/`aliyun-v2` 支持。
- `asr.vocabularyId` → paraformer `parameters.vocabulary_id`（热词表须先经 VocabularyService 预建、`target_model` 一致）；
  仅 `aliyun-8k`/`aliyun-v2` 支持。
- `asr.context` → inference `input.context`（领域语料）；**当前无 provider 支持**。
  - 依据：官方「提升识别准确率」支持列表**不含** `qwen3-asr-flash-realtime`（该模型无热词/上下文增强参数）；
    paraformer 系列只有 `vocabulary_id` 热词、无 `context`。故 `qwen3-asr-flash-realtime` 传热词/上下文/语言提示
    一律**忽略并记日志**（不报错）。
- 过滤逻辑为纯函数 `resolveAsrParams(preset, requested) → {…, ignored[]}`，有参数桩单测。

### 11.3 CosyVoice TTS provider（`src/voice/tts/aliyun.ts`）

- **接入方式**（官方当前推荐）：WebSocket `run-task` 协议，
  端点 `wss://{workspace}.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference`
  （通用域名 `dashscope.aliyuncs.com` 仍可用，专属域名官方建议迁移）；
  握手头 `Authorization: Bearer <apiKey>` + `X-DashScope-WorkSpace: <workspace>`。
  流程：`run-task`(input{}) → 收 `task-started` → `continue-task`(正文) → `finish-task` → 收二进制音频帧 → `task-finished`。
- **参数**（`payload.parameters`）：`text_type:"PlainText"`、`voice`、`format`(pcm/wav/mp3/opus)、
  `sample_rate`(8000/16000/22050/24000/44100/48000)、`volume`(0-100)、`rate`(0.5-2)、`pitch`(0.5-2)、
  `instruction`（方言/情感/角色，≤100 字）。
- **模型**：默认 `cosyvoice-v2`（`tts.model` 可覆盖）；系统音色默认 `longxiaochun_v2`（`tts.voice` 可覆盖）。
  - ⚠️ **模型与音色版本必须一致**：v2 模型只能用 v2 音色、v3 只能用 v3 音色，混用会返回
    `Engine return error code: 418`（如 `longanyang` 属 v3-flash/v3-plus，配 `cosyvoice-v2` 即 418）。
    本次自测已复现并据此把默认音色从误用的 `longanyang` 改为 v2 的 `longxiaochun_v2`。
- **播放（2026-10-15 改为流式，见 §15）**：合成改为**流式**——增量 `continue-task` 送文、二进制 PCM 帧**到达即写 AudioSink**（优先 stdin 流式播放器，否则分段临时 WAV 回退）；不再「整段合成→落盘→播」。下述旧的全量落盘/`player.ts` 文件播放器作为**分段回退**仍然保留。**合成跨平台**，文件播放器按平台择一：
  Windows `SoundPlayer`（pwsh 优先）/ macOS `afplay` / Termux `play-audio`（绝对路径 `$PREFIX/bin/play-audio`，带 `-s <stream>`）/
  Linux `/usr/bin/paplay`→`/usr/bin/aplay`；可用环境变量 `TTS_PLAYER` 显式覆盖、`TTS_STREAM` 设 Termux 音频流（默认 `media`）；
  **找不到任何播放器时抛清晰错误**（Termux 缺失明确提示 `pkg install play-audio`，其余含安装提示），不再静默无声。
  - ⚠️ **流式 WAV 头陷阱（2026-10-14 修；历史/兼容口径，生产无调用）**：CosyVoice 返回的 `format=wav` 是**流式 WAV**，其 RIFF 总长与 `data`
    块长度是占位值（约 `0x7fffffxx` ≈ 2GB）。`System.Media.SoundPlayer` 对此**不报错**，而是按占位长度读到即时 EOF →
    **静默不出声**（实测同一段 0.68s 音频：原样头 `PlaySync` 仅阻塞 11ms，修正头后 784ms，基线正弦 756ms）。
    **现状（与 `docs/ASYNC.md:43` 口径一致）**：流式路径固定裸 PCM、分段回退由 `audio-sink.ts` 用 `buildWav()` 自补 44 字节头，
    `normalizeWavHeader()`（`src/voice/tts/aliyun.ts`）**仅保留给历史/兼容与测试**，生产链路无调用；该函数对正常 WAV 幂等。
  - 另：合成返回 0 字节 → 直接抛错（不静默）；播放子进程**非 0 退出码**记 `error` 日志（此前仅忽略）。
- **`qwen3-tts-flash`（HTTP）**：仅 `voice`/`language_type`，无风格/语速 → 本轮不接入（`qwen-audio-3.x-tts` 情感靠文本内嵌标签）。
- **并发契约**：见 `docs/ASYNC.md` 交互点 ⑩。

### 11.4 忽略不支持参数

- ASR：`resolveAsrParams` 过滤，`voice-runtime` 对 `ignored` 记一条 stderr 日志（logger 无 debug 级别）。
- TTS：`ignoredTtsParams(provider, options)` 过滤，`tts/index.ts` 记一条日志；如 sapi 收到 `instruction`/`pitch`/… 只忽略不报错。

## 12. 语音 CLI（`emotions_cli` 工具 + `emotions-cli` 命令，2026-10-14）

> 背景：原 `speak` 工具把入参直接喂给内存里的 provider；改为 **CLI 风格**（照本机 `stats-command.js` 模式），
> 让「工具」与「命令行」共用同一入口，且模型只需给一条参数串。

### 12.1 工具契约（`emotions_cli`）

- 注册**单个**工具 `emotions_cli`（定义在 `src/voice/tool.ts`，由 server 入口 `src/emotions.ts` 的 `tool` 钩子注册），参数只有一个可选字符串 `args`；`execute` 把 `args` 拼成
  `node <cli> <args>` 用 `exec` 运行（`windowsHide: true`、`maxBuffer` 64MB），返回 `{ title, output }`。
- 未给 `args` → 视作 `help`；`speak` 自动补 `--background`（保持「不卡回合」）。
- **F10 联动拦截（2026-10-22）**：`execute(args, context)` 收宿主 `ToolContext`，若参数串以 `speak` 开头
  （词边界，含 `--follow`/`--background` 变体；`help`/`devices`/`status` 不拦）**且** `readAutoTts(context.sessionID)`
  为真（server 进程读 TUI F10 写的同一份**每会话状态文件**，缺文件/读失败=关=不拦）→ **不 exec CLI**、直接返回
  `{ title, output: <i18n `tool.speakSkippedAutoRead`> }`——防模型语音与自动朗读叠播。判定为纯函数
  `shouldInterceptSpeakForAutoRead(extra, autoReadEnabled)`（单测 `test/voice-tool.test.js`）；文案 execute 时经
  `safePhrases()` 现取（不用加载期缓存，`toolLanguage` 改后即时生效）。**auto-read 自身链路不经此工具**
  （`auto-read.ts` 直接 `spawn` CLI 派生 `speak --follow`/`--text-file` 子进程，见 §15.3），不会被拦截误伤。
- 兜底：先试 PATH 上的 `node`，失败再用 `process.execPath`（Bun 宿主下即 bun）。
- CLI 路径解析：`EMOTIONS_CLI_SCRIPT`（存在则用；旧名 `VOICE_CLI_SCRIPT` 兼容）> `<cwd>/dist/cli/emotions-cli.js` > 工具模块同级（`dist/voice/`，镜像后 `.opencode/plugin/voice/`）的 `../cli/emotions-cli.js`。CLI 位于**子目录** `dist/cli/`（镜像后 `.opencode/plugin/cli/`）：opencode 只自动 import `.opencode/plugin/` **顶层**的 `.js`，子目录不被扫描，故 CLI 启动时不会被误当插件执行。
- **入口保护**：`src/cli/emotions-cli.ts` 顶层只在 `isDirectEntry()`（`realpath(process.argv[1]) === realpath(本模块)`）为真时执行 `main()`；被 import 时无副作用、不打印（`main`/`isDirectEntry` 导出供单测）。回归测试见 `test/emotions-cli.test.js`「emotions-cli 入口保护」。

### 12.2 CLI 子命令（`src/cli/emotions-cli.ts` → `dist/cli/emotions-cli.js`）

| 子命令 | 说明 |
|---|---|
| `speak --text <t> \| --text-file <path> [--emotion <e>] [--voice <v>] [--rate <n>] [--provider <p>] [--background]` | 合成并播放；`--background` 立即返回（后台播放）；`--text-file` 从文件读正文 |
| `devices` | 列出本机音频输入设备（ffmpeg dshow） |
| `status` | 打印解析后的配置（`uiLanguage`/`toolLanguage`/provider/音色/语速/指令/凭证是否存在；**绝不打印密钥**） |
| `help` | 用法（随 `toolLanguage` 本地化） |
| `__play`（内部） | 由 `speak --background` 以分离进程调用，前台执行真正的合成+播放 |

> **自动朗读开关不在 CLI**：它由 TUI 的 `F10` 热键独占切换（模型不可经此工具/CLI 切换，无旁路），见 §14.2。

- 参数解析为纯函数 `src/voice/cli.ts` `parseCliArgs`（支持 `--flag value` / `--flag=value`、短名 `-t/-e/-v/-r/-p`；负数字面量可作取值）。
- **进程模型**：`speak --background` 在前台完成 **provider 名、云凭证、播放器可用性**（仅 `aliyun`）校验 后，
  `spawn(detached, stdio:"ignore").unref()` 派生 `__play`（参数经环境变量 `OC_VOICE_PLAY` base64 传递，
  不落命令行、不含密钥）；前台打印确认即退出。`__play` 靠子进程/WebSocket 句柄自然存活到播放结束。

### 12.3 已知限制（CLI 化的代价）

- **跨进程不保证打断**：同一次进程内 `speak()` 会先 `stop()` 上一条，但工具每次调用各派生独立 `__play`，两条并发朗读不会互相打断。
- **dispose 不再 stop**：分离播放进程无跨进程句柄，opencode 退出不会主动停止正在播放的语音（正常播完会自行退出）。
- 单机同一时刻的 provider 实例只在**单个 `__play` 进程内**唯一。

### 13.2 多语言（`src/lib/i18n.ts`）

- 配置键**拆成两个独立键**：`uiLanguage`（TUI UI 文案）与 `toolLanguage`（工具文案），默认均 `en`、可 `zh`；环境变量 `VOICE_UI_LANGUAGE` / `VOICE_TOOL_LANGUAGE`，旧名 `VOICE_LANGUAGE` 兜底两者（新名优先）。`resolveLanguage()` 大小写/区域不敏感（`zh-CN`→`zh`、`EN`→`en`），非法值回退默认 `en`。

- 新增语言：在 `LANGUAGES` 与 `PHRASES` 各加一项即可（类型会要求补齐全部键）。

## 14. 跨平台播放 + 自动朗读（auto_tts，2026-10-14）

> 背景：`sapi` 是 Windows 专有；`aliyun` 合成虽跨平台，但播放固定用 PowerShell `System.Media.SoundPlayer` →
> 非 Windows 静默不出声。另需「助手每条回复自动朗读」能力（初版为 CLI 可开关，**现改由 TUI `F10` 热键独占**，见下）。
> 同批把工具/CLI 更名为 `emotions_cli` / `emotions-cli`（对齐包名，防与其它插件重名）。

### 14.1 跨平台播放器抽象（`src/voice/tts/player.ts`）

- 按平台/可用性**择一**（`selectPlayer()`，纯函数式、`isAvailable/platform/env` 可注入便于单测）：

  | 平台 | 候选（取第一个可用） | 判定 |
  |---|---|---|
  | Windows | PowerShell `SoundPlayer`（`pwsh` → `powershell`） | PATH 探测 |
  | macOS | `afplay` | PATH 探测 |
  | Termux | `play-audio`（绝对路径 `$PREFIX/bin/play-audio`，默认前缀 `/data/data/com.termux/files/usr`），带 `-s <stream>` | `TERMUX_VERSION` 非空 或 `PREFIX` 含 `com.termux` 或平台 `android`；绝对路径判可执行 |
  | Linux | `/usr/bin/paplay` → `/usr/bin/aplay` | 按绝对路径探测（存在且可执行） |

- 环境变量 **`TTS_PLAYER`** 显式覆盖：已知 id 用其定义；`play-audio` 按 `PREFIX` 解析绝对路径；未知值视作命令名，以 `<bin> <file>` 调用。
- 环境变量 **`TTS_STREAM`**：Termux `play-audio` 的音频流类型（`media`/`alarm`/`notification`/`ring`/`system`/`voice`，默认 `media`）。Termux 缺失 `play-audio` 时报清晰错误并提示 `pkg install play-audio`。
- **找不到任何播放器 → 抛清晰错误**（含平台、已尝试候选、可安装的包、`TTS_PLAYER` 提示）；`aliyun provider.speak()`
  在发起时**同步**解析播放器，故错误能立刻冒泡（前台 `speak` 打印错误、后台模式在预检阶段拦下）。
- `sapi` 保持 **Windows 专有**：非 Windows 明确报错（`TTS_PROVIDER` 指路），不再静默无声。

### 14.2 自动朗读（`src/voice/auto-tts.ts` + `src/voice/auto-read.ts`）

- **开关**：由 TUI 的 **`F10` 热键**独占切换（`src/tui.tsx` `toggleAutoRead()`）。**模型/`emotions-cli`/`emotions_cli` 工具均不能切换**——
  原 `auto_tts` CLI 子命令、`status` 回显、工具文案已全部移除（无旁路）。`F10` **关闭时立即停止**正在朗读的那段（复用 `stopPlayback({ sessionID })`——按会话隔离，只停本会话/无主播放，见 §15.2），
  **开启**只影响后续助手回复、**不**补读历史；槽位末端 `🔊 F10` 段只做**状态显示**（亮=`success` 开 / 暗=`textMuted` 关，
  文本恒为固定串、不进模式语义；初值启动读一次状态文件，toggle 写成功后同步信号——除此无其它写入方，不需监听文件）。
  **键重复抑制（2026-10-20，修「按了状态不变」）**：按住 F10 会被 OS 连发按键事件（Windows 默认重复延迟 ~500ms、速率 ~30/s），
  逐事件切换会产生偶数次翻转、净效果=关；现用尾沿静默窗口 700ms（`shouldAcceptAutoTtsToggle`：每个事件都刷新窗口起点，
  一次物理按压只接受第一次切换；快速连按 <700ms 同样只算一次）。
- **共享状态（每会话一个文件夹，对齐 `plugins-cache/file-tool`）**：`~/.opencode/plugins-cache/opencode-emotions/<sessionID>/auto-tts`
  （内容极简 **`on`/`off`**，缺文件=关）；`AutoTtsOptions.dataDir` 注入的是**会话数据根**，内部再拼 sessionID 子目录。
  同一会话目录内另有 **`interrupt-req`**（2026-10-22 同日第六批）：会话级**中断请求水位**，内容=请求时刻（毫秒单值），
  写方=TUI 中断出口、读方=auto-read 每个派发单元前（口径见 §15.2/§15.3）；缺文件/非法内容读作 `0`=无请求。
  **原子写**（临时文件 + `rename`）；读/写失败一律降级（读→关；写失败返回 false，由 F10 提示）。因开关由 **TUI 进程**写、
  由 **server 插件进程**读，必须落共享文件而非内存。`src/voice/auto-read.ts` `drain()` 在**每次派生前再读一次开关**——
  关闭后队列里待播的下一段不再派生（关掉即停）。`tts-playback`（播放 PID）与 `tts/`（临时正文）**留 base 根**：
  打断只需按 PID、跨会话共用，挪动会牵动 CLI/tool 的 spawn 链。
- **重启不保留 → 每会话首见懒重置（2026-10-21 第七批，推翻旧「init 清整个 base」）**：TUI 初始化**不再**调
  `resetAutoTtsState()` 全清；改为本 TUI 进程**首次见到某会话**时（两触点：指示读 `autoReadOn` 求值、
   F10 `toggleAutoRead` 入口）调 `resetAutoTtsSessionOnce(touchedSessions, sid)` 只删**该会话目录**
   （`auto-tts` + `auto-tts-seen` + `interrupt-req` 同目录一并清，幂等；空/非法 sid 不入集合、不重置），
   记入模块级 `touchedSessions`（只增不减）。
  语义：**本进程首见 = 该会话从关开始**（重启 = 各自会话首见时重置）；后开窗口只重置它自己首见的会话，
  **不再误清其它窗口已激活的开关**。为什么作废旧取舍（日志实锤）：A 窗 F10 写 on（14:16:29）→ 中途开 B 窗
  触发 init 全清删掉 A 的 auto-tts → 回 A 窗灯读到关、F10 再按读 off 又写 on（14:17:09），看着「按了没反应」
  （指示灯/路由响应式本身正常）。`resetAutoTtsState()`（全量清）语义保留但**生产不再调用**（测试/人工维护）。
- **触发**：server 插件的 `event` 钩子。事件与取文本的**源码依据**（opencode v1.18.25）：
  - 助手消息完成：`packages/opencode/src/session/processor.ts:595-596` 置 `time.completed` 并 `updateMessage`；
    `packages/opencode/src/session/session.ts:629-633` 发布 `message.updated`（wire 名见 `packages/schema/src/v1/session.ts:596`）。
  - 插件 `event` 钩子见 `@opencode-ai/plugin` `dist/index.d.ts` `Hooks.event`；`message.updated` 只带 `info`（不含 parts），
    故用插件注入的 `client` 调 `session.message({ path:{ id, messageID } })` 取 `{ info, parts }`（SDK `SessionMessageResponses`）。
  - 只读 **text**：`Part` 联合含 `TextPart(type:"text")` 与 `ReasoningPart(type:"reasoning")`，按 `type` 过滤（排除 reasoning/thinking）。
- **朗读**：复用 CLI——正文写临时文件，`spawn(node, [cli, "speak", "--text-file", <tmp>])`（argv 数组，**不拼 shell 字符串**、
  不受命令行长度限制），分离 + `unref`，不阻塞；子进程退出后清理临时文件。
  **派生 bin**：默认 PATH 上的 `node`（env `VOICE_NODE_BIN` 可覆盖）——**不用 `process.execPath`**：server 插件进程里
  execPath 是 `opencode.exe`，`opencode.exe <cli.js> speak` 会立即失败退出（「触发了但没声音」根因）。
  **stderr 接管**（pipe）：子进程非零退出或有 stderr 输出时 `log.warn` 带片段，不再被 `stdio:"ignore"` 静默吞掉。
- **去重**：内存 + 每会话 `<sessionID>/auto-tts-seen`（每会话保留最后 50 条消息 id），防插件重启/事件重放重复朗读；`in-flight` 守门防并发重复。
- **并发契约**：见 `docs/ASYNC.md` 交互点 ⑫⑰。
- **Termux 采集限制**：`ffmpeg-static` 为 Linux x64 预编译，Termux 不可用 → 需 Termux 自带 `ffmpeg`/`sox` 并用 `FFMPEG_BIN` 指向。

## 15. 流式 TTS + 打断（barge-in）+ 增量自动朗读（2026-10-15）

> 背景：旧 `aliyun` 是「整段合成 → 落临时 WAV → 交给文件播放器」，首包延迟高；
> 且播放由不同进程发起（工具 CLI 子进程 / 自动朗读），用户发消息或语音输入时无法打断。本批一次解决。

### 15.1 流式合成 + 边收边播（`src/voice/tts/aliyun.ts` + `audio-sink.ts` + `stream-player.ts`）

- **协议**（照官方 CosyVoice inference）：`run-task` → 收 `task-started` → **多条 `continue-task`（增量送入，
  单条 ≤2 万、累计 ≤20 万、间隔 ≤23s，服务端自动分句流式合成）** → `finish-task`；音频经 **binary 帧**下发。
- **纯流式送文（阈值 + 增量）**：`createStreamChunker()`（纯函数，`stream.ts`）——**不做句切分**，
  文本按到达顺序增量送入多条 `continue-task`（由 CosyVoice 服务端自动分句）；**首次发送前缓冲到
  ≥ `tts.streamMinChars`**（默认 5，可配）才发出，之后**随到随发**；仅单条超 `MAX_CONTINUE_CHARS`(2 万)
  才硬切、累计超 `MAX_TOTAL_CHARS`(20 万) 抛错（服务端另有**相邻两条间隔 ≤23s** 约束，由发送节奏保证）。
  `runStream()` 在 `task-started` 后逐条 `continue-task`，最后 `finish-task`。
- **句切分只用于退化分段**：`splitSentences()`（`sentences.ts`）**不再**用于合成分块或 auto_tts 主切分；
  仅 `runSegmented()`（无流式播放器时的分段回退）按句边界落段。
- **边收边播**：`format` **强制 `pcm`**（裸 s16le 单声道）；WS `message` 收到 binary 帧**立即** `AudioSink.write(frame)`。
  `task-finished` 后 `AudioSink.end()` 等**真正播完**再结束 —— 不再整段落盘。
- **AudioSink**（`audio-sink.ts`）：
  - 首选**流式**（`stream-player.ts`）：吃 stdin raw PCM 的播放器——**Windows 内置 waveOut**（`pwsh`+`Add-Type`
    内联 C# 调 winmm，自实现**小缓冲有界队列**（≈40ms/块 × 最多 4 块 ≈ **160ms 预读上限**，2026-10-20 压缩：
    旧 8×16KB≈2.7s 会导致 CLI 被杀后孙进程把已排队音频播完的长尾音）连续无间隙、零外部依赖）→ `ffplay`；
    Linux `aplay -f S16_LE -r <sr> -c1 -t raw -` /
    `paplay --raw …`；Termux·macOS `play`(sox) / `ffplay`。
    `TTS_PLAYER` 只对**已知流式 id**（`waveout`/`winmm`/`aplay`/`paplay`/`sox`/`play`/`ffplay`）生效。
  - 回退**分段**：找不到流式播放器时，用 `player.ts` 的文件播放器（Windows SoundPlayer / Termux play-audio /
    macOS afplay / Linux paplay·aplay），**段边界 = 句边界**——provider 在每句音频收完后调 `sink.boundary()`
    落一段（`buildWavHeader()` 补 44 字节 WAV 头写临时文件后**顺序播放**；上一段播放期间继续合成下一句，减少间隙）；
    仅单句异常超长时按安全上限 `MAX_SEGMENT_SECONDS`(30s) 兜底。**分段路径一句一会话**（每句 `run-task→…→finish-task`），
    保证句边界处音频收齐。
  - 两条路径都不可用 → `selectAudioStrategy()` **同步抛清晰错误**（不静默）。
- **`instruction` 版本限制**：`supportsInstruction(model)` 判定，仅 `cosyvoice-v3`/`v3.5` 与 `qwen-audio-3.x`；
  默认 `cosyvoice-v2` **不支持** → provider 忽略指令并记一条日志（`buildCosyVoiceRunTask` 仍如实按入参构造，便于单测）。
- **取消**：`buildCosyVoiceCancelTask()` = `finish-task` + `payload.input.directive="cancel"`；`stop()` 时发出并关连接。

### 15.2 打断（barge-in）

- **触发点**：① **用户发送消息** → server 插件 `src/emotions.ts` 的 `chat.message`（输入是 `UserMessage`，仅在用户发消息时触发）；
  ② **语音输入 `F8`/`F9`** → TUI 插件 `src/tui.tsx` 的 `toggleMode()`（2026-10-22 起诊断埋点 `f8f9 interrupt: stopped=… session=…`，
  核实「F8/F9 到底有没有停掉播放」；停播后 follow worker 死亡的连带链见下条「F8/F9 中断的正确性链路」）；
  ③ **自动朗读 `F10`（双态，2026-10-22）** → `toggleAutoRead()`：**本会话（或无主）有活跃播放**时按键 = **只中断播放、不切开关**
  （`isInterruptablePlaybackActive(sessionID)` 判活 → `writeInterruptRequest(sessionID)` 写会话级**中断请求水位** +
  `stopPlayback({ sessionID })` + toast「已中断播放（朗读开关状态未变）」，
  **不写状态文件、不 bump 指示灯修订号**，开关与灯原样；置于键重复抑制之后，按住连发只处理第一个 accepted 事件）；
  **无活跃播放**才走原 toggle 语义（切 off 时同样 `stopPlayback({ sessionID })`）；
  ④ **TUI 窗口退出/关窗** → `api.lifecycle.onDispose` → `stopPlaybackForSessions(touchedSessions)`（遍历本窗口**见过的**会话逐个带会话语义停——
  修「Ctrl+C 退出还在读」：旧 dispose 只停语音输入 runtime，TTS 的 CLI worker + PowerShell 孙进程成孤儿继续播，2026-10-21 第七批）。
- **动作（2026-10-21 起按会话隔离；同日第五批改多条目 = 跨会话混音、单会话互斥）**：`stopPlayback({ sessionID })`
  按 PID 停止播放——**带 sessionID 时只停「同会话键 + 无主（条目无 sessionID）」的播放**，跨会话有主条目不杀不清
  （修「另一窗口新会话的消息把本会话正在播的 sapi follow worker 杀在句中」的误杀；产品口径：不同会话 TTS
  **同时播放**——Windows 混音器天然多流并存，B 会话开播**不杀** A 会话、**不做排队**）；
  **无参（或 sessionID 空）→ 停全部条目**（全清路径；TUI dispose 已改**逐会话遍历**本窗口 `touchedSessions`，见触发点④）。
  被 `SIGTERM` 的播放进程在信号处理器里向 provider `stop()`（云 TTS 发 `directive=cancel`）后退出。
- **F10 判活 helper（2026-10-22，`src/voice/playback-state.ts` `isInterruptablePlaybackActive(sessionID, nowMs?, options?)`）**：
  与 `stopPlayback` **同源同口径**（同一 `loadMap` + 同一道会话归属门：`sessionID` 非空只看「本会话键 + 无主键 `_`」，
  禁碰其它会话；空 = 全部条目）。「活跃」判据（满足其一）：`pid`/`playerPid` 存活（`isProcessAlive`，可注入），
  **或** `startedAt + PLAYBACK_TTL_MS` 未过期（条目尚新鲜——防「刚登记 playerPid 未补写 / 刚死亡条目未清」窗口期漏判；
  超 TTL 条目在 `loadMap` 读取时即清、天然 false）。纯读无副作用，单测 `test/playback-state.test.js`「判活」组。
- **F8/F9 中断的正确性链路（2026-10-22 逐行取证，链路真实存在）**：`toggleMode` 的
  `stopPlayback({ sessionID })` 杀掉 follow worker 的 CLI `pid`（+`playerPid`）→ worker 子进程 `exit` 事件置
  `worker.dead=true`（`auto-read.ts:904-906`），stdin 写 EPIPE 同样置死（`:924-928`）→ 下一句单元
  `writeWorkerLine` 抛「follow worker 不可用」（`:942-944`）→ `deliverUnit` catch 后 `markInterrupted([messageID])`
  + 清队列/carry（`:1023-1027`）→ 该消息**停读**、后续 delta 一律丢弃，**不影响下一条消息**。
  唯一延迟面：kill 与 `exit` 事件送达之间的已缓冲写（≤1 单元写进已死管道、无人播放，下一个单元即抛错置位）。
  **链路边界（2026-10-22 同日第六批补）**：该链路只在「**已有进程被杀中**且**后续确实发生写失败**」时才置位——
  按键落在两个单元之间（无可杀进程=杀空）、或 worker 已死而该消息改走非 follow 分支重新 spawn（杀后重生），
  两条都**不经过**写失败 ⇒ 由下面的「会话级中断请求水位」兜住（同批修复，不推翻本链路）。
  **「不能自己中断自己」边界（同批取证）**：`tts-playback` 的**唯一写入方**是 CLI `registerPlaybackLifecycle`
  （`src/cli/emotions-cli.ts:120-149`，`writePlayback` 全仓仅此一处调用）；语音输入 runtime（`src/runtime/voice-runtime.ts`，
  麦克风进程）**从不写播放条目**（grep 无 `playback-state` 引用）⇒ `stopPlayback` 按 PID 结构上杀不到 runtime，F8/F9 开麦
  与停播互不伤身。
- **会话级中断请求水位（2026-10-22，修「按 F10 中断后剩余文本继续播」）**：`stopPlayback` 是**按 PID 杀**的跨进程动作，
  结构上有两个拦不住的缺口——① **杀空**：按键落在两个朗读单元之间（worker 播完上一句、下一句还没投递），此时没有任何
  登记在册的播放进程；② **杀后重生**：follow worker 被杀后该消息走 `deliverUnit` 的非 follow 分支**重新 spawn** CLI。
  服务端插件进程对「用户按了中断」原本一无所知 ⇒ 中断意图必须**跨进程落文件**：
  **写方**=TUI 的两个中断出口（F10 双态中断分支、F8/F9 `toggleMode` barge-in）**先原子写**
  `~/.opencode/plugins-cache/opencode-emotions/<sessionID>/interrupt-req`（内容=请求时刻，`writeInterruptRequest`）**再**
  `stopPlayback`（停播抛异常时意图也已落盘；取不到会话路由则**不写**，保持「无主」语义）；
  **读方**=server 侧 auto-read 在**每个派发单元前同步读一次、不加缓存**（`applyInterruptRequest`：
  `deliverUnit` 入口=follow 写前=非 follow spawn 前的唯一派生入口，另在 `runFallback` 整段读前补一处）。
  **时序契约**：请求时刻**严格大于**该消息开始时间 ⇒ 命中 ⇒ 走与 `interrupt()` **同一套**打断执行体
  `stopInFlight(sessionID, 请求时刻)`（置 `interrupted` 水位＋清队列/carry＋按归属只 kill 本会话且早于水位的子进程）；
  开始时间取服务端 `info.time.created`（权威），否则插件首次观察时刻（`messageStarts` 记账）。
  水位是**会话级时间戳**而非布尔 ⇒ 「开始时刻 &lt; 请求时刻」的在途消息全停，**晚于水位的新消息不受影响**
  （F10 双态只停声、开关没变 ⇒ 后续回复照常读）；相等不算命中；无记账/读失败一律**放行**（宁可漏拦不可误杀）。
  该文件在**会话目录内**，随 `resetAutoTtsSession()` 整目录删除一起清（不进 `AUTO_TTS_RESET_KEEP_NAMES`）。
- **会话归属的传递链**：auto-read `spawnSpeak`/`spawnWorker` 派生 CLI 时 env 注入 `EMOTIONS_SESSION_ID=<消息 sessionID>`
  （`PLAYBACK_SESSION_ENV`，**走 env 不改 argv**）→ CLI `registerPlaybackLifecycle()` 登记进条目；
  打断方取 `input.sessionID`（`chat.message`）/ `currentSessionID(api)`（TUI F8/F9）/ 当前 `sessionID`（F10）。
  **手动 speak（`emotions_cli` 工具/命令行）不设该 env ⇒ 条目无主，任何消息可打断（有意兼容）**。
- **跨进程**（`src/voice/playback-state.ts`）：播放进程（CLI `speak` / 分离 `__play` / follow worker）启动时把
  `{ pid, playerPid?, provider, taskId, startedAt, kind, sessionID? }` **原子写**到 `~/.opencode/plugins-cache/opencode-emotions/tts-playback`——
  文件为**多条目 JSON map** `{ [sessionID]: entry }`（**每会话一键、并行播放互不覆盖**；无主（手动 speak）与
  **旧单条格式**（顶层有数值 `pid`）读作哨兵键 `_`=`PLAYBACK_OWNERLESS_KEY`，entry 内 `sessionID` 字段保留 →
  归属门仍按字段保护跨会话；每次读写顺带清 TTL 陈旧条目并落盘）。
  （`playerPid` 为可选字段，**真正发声的孙进程** PID——sapi 的 PowerShell；`speak()` 同步返回后经
  `TtsProvider.activePlayerPid?.()` 一次补写，无轮询；旧格式无该字段兼容读）；
  启动新播放前先 `stopPlayback({ sessionID: env EMOTIONS_SESSION_ID })`（**只清本会话+无主**＝单会话互斥、
  跨会话混音；无 env（手动/工具路径）= 无参全清既有语义），退出/播完 `clearPlayback(pid)`
  （删**含该 pid 的条目**，可能多条）。
  打断方**先过会话归属门**（带 `sessionID` 且条目 `sessionID` 存在且不等 → 跳过并记一行 info），再对记录的
  `pid` **与 `playerPid` 两个目标各自过红线后都终止**（Windows `TerminateProcess` 不杀子孙，
  只杀 CLI `pid` 会让孙进程把当前块播完）：**先 `SIGTERM`，有界超时（1.5s）后仍存活再 `SIGKILL`**。
  成功停止记 info `stopped playback session=<sessionID 或 -> provider=<…>`（logger `playback`）。
  **红线**：每个目标都必须是本插件自己派生的进程，且 `pid>1`、`pid≠自身`、`not startedAt<now-TTL(30min)`；
  无记录/已退出/陈旧/文件损坏一律**静默降级**；**严禁按进程名/模式杀**（`kill`/`isAlive`/`now` 可注入以便单测）。

### 15.3 增量自动朗读（`src/voice/auto-read.ts`）

- **分会话开关（2026-10-20，同日再改：每会话目录 on/off 单值）**：状态在 **`<root>/<sessionID>/auto-tts`**（内容 `on`/`off`；缺文件=关）。
  `readAutoTts(sessionID)` / `writeAutoTts(sessionID, enabled)`（每会话独立文件，无读-改-写竞争面）；非法内容一律按关降级。
  **一个会话的 F10 开关不影响其它会话**；重置改**每会话首见懒重置**（本 TUI 进程首见该会话才删其目录、再见不删；
  init 不再全清整个会话数据根，见 §14.2「重启不保留」）。
  **F10 键重复抑制**：尾沿静默 700ms（`shouldAcceptAutoTtsToggle`），按住被 OS 连发按键事件时一次按压只切换一次。
- **子会话硬跳过（2026-10-20）**：server 侧按 sessionID 单飞 `client.session.get` 取 SDK `Session.parentID`
  （字段名依据：`@opencode-ai/sdk` `dist/gen/types.gen.d.ts:469` `parentID?: string`；`SessionGetResponses` 200=`Session`，同文件 :1913），
  缓存 `sessionID→是否子会话`（进程内永久）；**是子会话 → 无论开关开没开都不读**（early return，
  `handlePart`/`handleDelta`/`runFallback`/`drain` 全覆盖）。delta/part/drain 路径在判定未完成期间按「子会话」处理
  （fail-closed，防子会话首条消息漏读；text-end 快照会在判定完成后恢复父会话），fallback 路径 await 判定完成再决策。
  TUI 侧按 F10 时用 `api.state.session.get(sessionID)?.parentID` 同步判定，是子会话则 toast「子会话不自动朗读」且不写状态文件。
- **事件**（2026-10-20 修正，根因见 `docs/changes/设计-语音输入注入.20261020.md`）：文本流式的**真增量通道是
  `message.part.delta`**（`text-delta` → `session.updatePartDelta`，payload 只有
  `{sessionID, messageID, partID, field:"text", delta}`，**无 part、无类型、无 role**）；
  `message.part.updated` 仅在 **text-start**（空快照）与 **text-end**（全量快照）各发一次——旧实现只订
  `message.part.updated` 拿不到流式增量，退化成「输出完成后整段读」。现口径：
  - `message.part.updated` 起始快照**登记 `partID→type`**（reasoning 也走 delta、payload 无类型，必须靠它过滤），
    并以全量文本**校准**已累计文本（快照不短于已送偏移时以快照为准，比 delta 抗丢失）；
  - `message.part.delta` 按登记表过滤后**增量追加**送入 TTS（`field` 只认 `text`；`synthetic`/`ignored` 不读）。
- **只读 assistant 的 text**：part/delta 都不带 role → 先用 `message.updated` 的 `info.role` 建立
  `messageID→role` 表；**未知时惰性补取一次**（`fetchMessageRole` 经 client 取 `info.role`，单飞去重）。
  **被角色门挡过事件的 part 置 `tainted`、其 delta 全丢**（不变式：part 的 `text` 恒为真实文本前缀 →
  快照 `pending=slice(flushed)` 无重复无丢失）；摘要消息（`summary===true`）不读。
- **阈值 + 增量串行 + 凑批合并 + 句对齐切分 + sapi follow worker（2026-10-21，同日两批）**：与流式合成**同一口径**
  `createStreamChunker()`（`tts/stream.ts`）——**缓冲到 ≥ `tts.streamMinChars`**（默认 5）才**首次**开始派生，**此后随到随发**。
  同一消息的朗读进**串行队列**（`drain`），每轮 shift 首块（前置 carry 尾段）后把**此刻已在队列**的块**合并**
  （单次 ≤ `DRAIN_MERGE_MAX_CHARS`(2000) 字，超出留队列下次读；**事件驱动：不等待/不轮询新 delta**），
  再经 `splitDrainUnits()`（内部 `splitSentences()`）**句对齐切分**：完整句按 ≤2000 **贪婪连读**成单元、
  **未完结尾段 carry 到下一批**（块边界落在句尾——非 sapi provider 的段间停顿因此落到句尾）、
  **单句超上限才句内硬切**（唯一句中断点）、无标点 carry 超上限兜底硬切（防无限攒到 done）。
  - **sapi follow 常驻 worker（真修冷启动）**：provider 能力位 `TtsProvider.followSupport`（仅 sapi=true）为真时，
    消息首个句单元派生**一个** `emotions-cli speak --follow` worker（stdin 保持打开），后续单元
    `worker.stdin.write(line+"\n")` **不再每块 spawn/await 退出**——PowerShell 整 worker 生命周期只冷启动一次
    （`SAPI_FOLLOW_SCRIPT`：`[Console]::In.ReadLine()` 循环 + stdin UTF-8，`$syn.Speak` 同步=天然串行）。
    `finalize` 关 stdin（EOF）并 await worker 退出冲刷尾音（外层 30s 超时强杀；worker CLI 内 `followEnd`
    另有 30s 等 PowerShell）。worker 记入 `activeChildren`（`Map` 带 messageID/sessionID 归属；`interrupt(sessionID)` 只杀本会话、无参全杀）；worker CLI 启动即登记
    `tts-playback`（pid+playerPid=常驻 PowerShell）→ `stopPlayback` 双杀即静音。**worker 中途天折**：写失败 →
    warn + 该消息置 `interrupted`（水位同语义：不再补读），**不影响下一条**；spawn 失败 → 退回按块 spawn。
    `--follow` 与 `--text`/`--text-file`/`--background` 互斥，provider 不支持时 CLI i18n 报错 exit 1；
    普通 `speak --text`（手动/工具路径）**行为完全不变**。非 follow provider（aliyun/mimo/termux）仍每单元
    spawn CLI，但块粒度已是句边界。日志：worker 启动 1 条 info + 块级静默（`Logger` 无 debug，保持 info 低噪）；
    非 follow 路径保留每单元 `自动朗读已触发：… len=…`（`chunks_merged=` 已随句对齐移除）。
  - `drain` **每次派生前再实时读一次该会话的开关文件**（`F10` 关闭即清空队列/carry、不再播下一段，并关 worker）——
    delta 高频路径读开关走**按 sessionID 分键的 300ms TTL 缓存**，立即停由 drain 的实时读保证。整体为「增量转发 + 块内流式」。
- **空文本跳过（2026-10-21）**：`spawnSpeak` 与 CLI `speak` 入口对纯空白正文**直接跳过**（不写临时文件、不派生、不报错）——
  否则 CLI 侧 trim 后为空 → provider 抛「text 不能为空」→ 子进程异常退出 warn（用户实测）。
- **完成补读 / 回退**：消息完成时 `chunker.flush()` 补读未达阈值的缓冲并置 `seen`；**未观察到 part 更新**
  的消息在完成时回退「整段读」（旧行为）。
- **诊断**（info、**每消息一条汇总**，可长期开）：`自动朗读汇总：message=… session=… path=stream|fallback|skip
  skipReason=… parts=… deltas=… roleMiss=… skips=… chunks=… chars=…`；角色惰性补取另打一条
  `自动朗读角色补取：message=… role=…`；子会话判定另打一条 `自动朗读子会话判定：session=… child=…`。
- **去重**：内存 + 每会话 `<sessionID>/auto-tts-seen`（每会话保留 50 条）；同一 `messageID` 只读一次。
- **打断（2026-10-21 改为水位语义；同日第四批按会话收窄）**：`interrupt(sessionID?)`
  （`chat.message` 触发，传 `input.sessionID`）清空**目标范围**待读队列、kill **目标范围**朗读子进程，
  并对**目标范围的在途消息**（`streams` 有状态的 ∪ `diag` 已过门但尚无状态的，按 `state.sessionID`/
  `diag.sessionID` 过滤）置 `interrupted` 位；置位后这些消息的 delta/part 新块**一律丢弃**、`enqueue`
  拒收、完成时**不补读**（直接 `seen.add` 封口，防「完成回退整段读」把被打断的整条又念一遍）；
  **新 messageID 不受影响**（下一条消息正常读）。**带 sessionID = 只处理该会话**（另一会话的队列、水位、
  `activeChildren` 子进程一律不动，修「A 会话发消息腰斩 B 会话朗读」）；**无参或空白 = 全清**
  （dispose/进程退出清场路径保持原语义）。残余：插件启动后从未收到任何 part/delta 的消息无从识别
  （streams/diag 均无其条目），完成时仍可能回退整段读。
- **打断的第二条入口＝会话级中断请求水位（2026-10-22 同日第六批）**：上面的 `interrupt()` 只能由**同进程**
  （`chat.message`）触发，而 F10/F8/F9 的中断在 **TUI 进程**里、只够着 `tts-playback` 的 PID——**单元间隙杀空**与
  **worker 死后非 follow 分支重新 spawn（杀后重生）**两类情形拦不住（用户实测「按了 F10 剩余文本还在播」）。
  现口径：TUI 写 `<sessionID>/interrupt-req`（请求时刻）→ auto-read 在**每个派发单元前**同步读
  （`applyInterruptRequest`：`deliverUnit` 入口 + `runFallback` 整段读前），**严格大于**该消息开始时间
  （`messageStarts`：服务端 `info.time.created` 优先、否则首次观察时刻）⇒ 命中，调 `stopInFlight(sessionID, 请求时刻)`
  ——与 `interrupt()` **同一套**执行体（只是多了时间收窄），不复制第二份水位/清队列/杀进程逻辑。
  命中后：该消息 delta/入队丢弃、完成不补读（`seen` 封口）、本会话早于水位的在途子进程被 kill；
  **晚于水位的新消息照常读**（F10 开关未动）。读失败/无文件/无开始时间记账 ⇒ **放行**（宁可漏拦不可误杀）。
- **并发契约**：见 `docs/ASYNC.md` 交互点 ⑫⑬⑰。

### 15.4 已知取舍

- **自动朗读的进程模型（2026-10-21 真修后）**：`drain` 凑批合并 + **句对齐切分**（块边界落句尾）；
  **sapi 走 follow 常驻 worker**（每消息 1 次 `speak --follow` spawn，PowerShell 整消息只冷启动一次，
  句块经 stdin 行连续喂入——段间无冷启动停顿）；**非 follow provider（aliyun/mimo/termux）仍每句块 spawn CLI**，
  块内是流式、块间有进程开销（但停顿已对齐句尾）。worker 是**每消息一个**（finalize 即关），
  消息之间仍有一次 spawn；跨消息复用 worker 需引用计数与打断语义细化（本轮未做）。
- **句对齐的延迟代价**：首个朗读单元等到**第一个句末标点**（或消息完成）才发出——`streamMinChars` 阈值
  仍管「何时开始缓冲」，句边界管「何时派生」；对散文回复影响小（首句通常数秒内闭合），
  对长时间无标点的输出（代码/列表）会攒到 done 或 carry 超 2000 兜底硬切。
- **Windows 已自带流式播放器**：内置 waveOut（`pwsh`+winmm）不再依赖 `ffplay`；`pwsh` 缺失时回退 `powershell`
  （启动略慢、`Add-Type` 编译缓存因运行时不同可能重新编译，可接受）。内置播放器首次运行会 `Add-Type` 编译内联 C#，
  缓存 DLL 到 `%TEMP%`，后续同运行时起播开销约数百毫秒（follow worker 模式下每消息仅一次，听感可忽略）。
- **分段路径的句边界**：为保证 `boundary()` 时该句音频已收齐，分段路径**一句一会话**（每句独立 `run-task`→`finish-task`），
  比流式路径多几次会话/连接开销；换得精确句边界与更少段间间隙。
- **`v2` 不支持 `instruction`**：已据实忽略并记日志（换 `cosyvoice-v3`/`v3.5` 才生效）。
- **手机端槽位字形（2026-10-21 查证，结论：无代码解法，不改图标）**：用户手机端现象=① `🎙`/状态圆圈**变扁变形**
  ② `●`↔`⏳` 切换**非居中、左对齐、闪烁**。一手证据（Node `\p{…}` 属性 + `dist/voice/slot.js` 实测）：
  - `🎙` U+1F399：`Emoji=Yes` 但 **`Emoji_Presentation=No`** → 默认按**文本呈现**绘制，而槽位口径（同渲染库
    `string-width@7`/`Bun.stringWidth`）计 **2 列**，字形被塞进 2 格框 ⇒ 观感压扁，属**终端字体度量**，插件侧无解；
  - `●` U+25CF / `○` U+25CB：`Emoji=No`、East Asian **Ambiguous** → 口径计 1 列（手机端显示正常，与之一致）；
  - `⏳` U+23F3：**`Emoji_Presentation=Yes`** → 默认 emoji 呈现、口径计 2 列；状态字形字段固定宽 **Wg=3**
    （`⏳ ` 占满 3、`●` 补到 3），切换闪烁源于**终端实际进格数与口径不一致**（手机端把 `⏳` 当 1 列推进），
    不是补空格位置问题；
  - **VS15（U+FE0E）路线否决**：`displayWidth("\uFE0E")=0`、`displayWidth("⏳\uFE0E")=2`（已补单测锁定）——
    加 VS15 只请求终端改画窄字形，本插件与渲染库的布局**仍按 2 列预留** ⇒ 错位方向不变甚至更糟，且桌面端
    （按 2 列绘制）会被反向带偏；
  - **居中填充路线否决**：把 `padToWidth` 的右补改成两/中补，字段总宽不变、**修不了「终端少进一格」**，
    却会改动桌面端既有观感与多条逐字断言；
  - **唯一能静态消除该错位的做法=让三个状态字形同宽**（把启动中的 `⏳` 换成非 emoji 的窄字形，如 `◐` U+25D0，
    与 `●`/`○` 同属 Geometric Shapes + Ambiguous ⇒ Wg 由 3 降为 2、总宽各 -1）——**属产品决定**（换用户可见图标 +
    改 `GLYPH_SEGMENT_WIDTH`/逐字断言），未擅自执行，需由用户拍板。
  - **同日第十批后的现状**（2026-10-21 用户指令改图标形态，本条查证部分失效）：`🎙` 图标段与 `●`/`○` 圆圈段**已删除**，
    新图标 `⇥`(U+21E5)/`⤉`(U+21C9) 均为 East Asian Ambiguous 的非 emoji 箭头 ⇒ 口径与实际进格都是 **1 列**，
    「圆圈/🎙 变扁」现象随之消失；**残留风险仅剩 `⏳` 忙前缀**（仍是 `Emoji_Presentation=Yes`、口径 2 列、段宽 **Wb=3**
    定宽占位）：手机端若把它当 1 列推进，前缀出现时该段仍会少进一格。未换成窄字形（如 `◐`）——**用户指定用 `⏳`**。
  - **同日第十一批后的现状**（2026-10-21 用户指令：恢复 `🎙` 常驻段 + `⇥`→`↧`）：
    `🎙`(U+1F399) 重新作为**最前常驻段**（口径 2 列 + 尾随空格 = 段宽 3，总宽 17 → 20），
    手机端「emoji 塞进 2 格框压扁」的观感**随之回来**（属终端字体度量、插件侧无解，见上）；
    输入组图标 `⇥`(U+21E5) 换成 `↧`(U+21A7)（用户反馈 `⇥` 与 `F8` **重叠**）——两者同属 Arrows 块 U+2190–U+21FF、
    East Asian Width 同为 Ambiguous ⇒ **口径与实际进格都仍是 1 列，宽度与定宽契约不受影响**；
    `⤉`(U+21C9) 与 `⏳` 忙前缀的处置（含上述手机端残留风险）**不变**。
  - **同日第十二批后的现状**（2026-10-21 用户指令：`⏳` 与 `🎙` 共用最前一格、删独立忙占位段）：

## 16. 回环防护：半双工静音门（2026-10-22）

### 16.1 为什么需要门（探针一手证据，非推测）

自动朗读开着时，喇叭放出的 TTS 会被同一台机器的麦克风录进去 → ASR 出 final → 注入/追加 →
模型再回复 → 再朗读，形成**自激回环**。原指望系统 AEC（回声消除），2026-10-22 实测探针结论为
**unsupported**（方法：`ffmpeg -f dshow` 录「麦克风 (USB Audio)」+ 插件 CLI `speak` 播放 + WAV 多窗 RMS）：

| 窗口 | 时间 | RMS | dBFS |
|---|---|---|---|
| 基线（独立 2s 静音） | 0–2s | 0.000240 | -72.4 |
| 基线窗（主录音前段） | 0–0.45s | 0.000077 | -82.3 |
| **播放窗（峰值 500ms）** | **1.80–2.30s** | **0.004609** | **-46.7** |
| 播放后窗 | 5–6s | 0.000442 | -67.1 |

- **播放窗 / 独立基线 = 19.2 倍（25.7 dB）**，判据为「≥ 基线 3 倍（≈10 dB）即录到回环」→ 远超阈值，
  且播放窗包络形状与 speak 触发时序吻合（0.5s 触发 + 合成延迟 ≈1.3s ⇒ 1.8s 出声）。
- 原始 dshow 采集路径上**没有生效的 AEC**（设备类 `Filter` 值全空，仅微软标准 proxy）。
- 报告与产物：`.tmp/scratch/aec-probe-report.md`（帧序列 `aec-probe-analysis.txt`、录音
  `aec-probe-main.wav`/`aec-probe-baseline.wav`、分析脚本 `aec-probe-analyze.mjs`）。

⇒ 按既定口径走**「播放时闭嘴」的半双工兜底**：TTS 播放期间丢弃 ASR final，掐断回环。

### 16.2 口径与接线（门只做「分发层不消费」）

- **不在 runtime/ffmpeg 层做任何静音**：采集与识别照常跑，只在 **TUI 分发层**丢掉结果——
  避免把「听不见」做进采集链（用户随时可以只关朗读而不动麦克风）。
- **接线点**：`src/tui.tsx` 的 `dispatch()`（RuntimeFinal 分发入口）**最前面**过门：
  活跃 → 一条 `log.info`（`asr gate drop: session=… active=… sinceActiveMs=… text=…`，文本预览
  `ASR_GATE_PREVIEW_LEN`=20 字符）→ `return`；**不 toast、不注入（`session.prompt`）、不追加（`appendPrompt`）**。
  `ready` / `error` / `done` 事件**不经过**门（照旧）。
- **范围铁律（归属口径不得另造）**：判活**只复用** `src/voice/playback-state.ts`
  `isInterruptablePlaybackActive(sessionID, nowMs?)`——与 `stopPlayback`、F10 双态中断**同一道会话归属门**，
  只看**本会话键 + 无主 `_`** 条目，**其它会话的播放一律不算**（不误吞别的会话说话时的输入，也不越界读别人）。
  取不到会话路由时传哨兵键 `PLAYBACK_OWNERLESS_KEY` ⇒ **只算无主播放**（宁可漏拦也不越界；
  **禁止**用空串 `""`，那是「全部条目」口径，单测已钉死两者差异）。
- 门**不调 `stopPlayback`、不杀任何进程**（与打断链解耦）；门条件抽成纯函数
  `src/voice/asr-gate.ts` `shouldDropAsrFinal(playbackActive, lastActiveAt, now, tailMs)`，接线极薄。

### 16.3 尾音缓冲（`ASR_GATE_TAIL_MS` = 500ms）

- 播放结束后的 **500ms 内仍算活跃**（覆盖尾音/混响：内置 waveOut 播放器 EOF 后只播完已排队的 ≈160ms，
  再加房间混响与「刚停就开口」的话头）。
- 实现：TUI 闭包 `lastInterruptableActiveAt`（**窗口级**状态，每 TUI 进程一份、跨窗口不同步）——
  `dispatch()` 每次判活为真就刷新为当刻；门条件 = `活跃 ∥ (now - 起点 < tail)`。
  起点 `0` = 本进程从未观察到活跃 → 放行。窗口边界取**严格小于**（恰好 500ms 即放行）；
  时钟回拨（`now < 起点`）按「仍在窗口内」保守丢；`tailMs<=0` = 关闭尾音窗口。
- **不缓存 playback 状态**（选它而非缓存的理由）：ASR final 频率低（一次说话才一条），每次直接读一个
  JSON 文件比维护缓存**更便宜**、且不会读到陈旧值（helper 内部顺带清 TTL 陈旧条目）；
  门内 `Date.now()` → 判活 → 刷新起点 → 纯函数判定 → `return` 全在**同步段**，无 await 交错（并发契约见
  `docs/ASYNC.md` 交互点 ⑦⑧）。

### 16.4 半双工代价与门的释放（预期行为，不是缺陷）

- **代价**：朗读期间用户说话会被**吞掉且不可恢复**（不排队、不补投）——这是「半双工」的字面含义，
  是换取「不回环自激」的有意取舍，**属预期行为**。
- **要说话的正规姿势**：先按 **F8/F9**（`toggleMode` 入口即 `writeInterruptRequest(sessionID)` 写会话级中断水位 +
  `stopPlayback({ sessionID })` 停播）或 **F10**（双态：有活跃播放时只中断播放，同样**先写水位再停播**）——
  **停播后门自动释放**：条目被清 / 进程不再存活，下次
  `dispatch()` 判活即为假，再加上 ≤500ms 尾音窗口即可正常输入（无需任何显式开关）。
- 残余：500ms 覆盖不住特别长的混响时，停播后仍可能多丢一条；窗口调大则吞用户话更多（取值见
  `src/voice/asr-gate.ts` 注释）。跨窗口场景（另一 TUI 进程的播放）按口径**不算**，回环风险自担
  （两窗口同会话互停本就是已知取舍）。

### 16.6 软 AEC 阶段 1 离线实测：不通过（no-go），维持本门（2026-10-22）

- **依据① AEC3 算法本身可用**：合成宽带信号 ERLE **34.4 dB**（活跃 **35.6**、稳态 **45**），复现选型调研值
  ⇒ 失败不在算法，在本机采集链。
